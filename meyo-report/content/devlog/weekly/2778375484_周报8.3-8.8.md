2)  **架构短板追齐DeepAgents/Hermes/Claude Code**：系统能自己朝目标校准+自己产生新tool并注，具体补齐：

**5）性能提速：**

| 项 | 优化前→优化后 | 方法 |
| --- | --- | --- |
| 搜索fanout | 22-36s → 1.1s | 一次搜索请求"广撒网"到多个搜索源/多个query变体并发执行的过程。之前每次fanout都会额外调一次LLM做"监督决策"，相当于每次搜索都要多等一轮大模型往返，这是不必要的开销，砍掉后从22-36s压到1.1s，是搜索链路里最基础也最高频的一环，提速收益会被后面所有依赖搜索的能力（问答、深度研究）放大受益。 |
| 推理题(马拉松) | 246s → 35.9s（7倍） | 指那种不需要检索、纯靠模型自身推理链条就能解的题（比如数学、逻辑推理），如果架构上"不信任模型直接推理"，会误判成需要检索的题，白白走一遍搜索+蜂群的重流程，这类题该走"直通车"，越快越好 |
| 蜂群evidence阶段 | 145-231s → 24-48s（降67%） | `deep_research_swarm`（多个子agent组成的搜索蜂群）里负责各自并行搜集证据的阶段。简单事实题不需要蜂群全力以赴地深挖，走轻量路径就能拿到答案，这是"好钢用在刀刃上"——难题不阉割，简单题不浪费算力。 |
| 系统审计器 | 62.7s → 2.5s（25×） | 全项目"代码接线一致性"审计工具，检查"某个模块/函数是否真的被其他地方调用了"（防止"建了没接"的死代码）。它本身是个诊断工具，跑得慢会拖累依赖它的上层监控（supervisor）误判系统为"BROKEN"状态，属于典型的"工具本身的性能问题被误诊为业务故障"。 |
| CPU 优化 | 优化快模型和cdp路由问题 | 系统里模型调用分了"轻量级任务用便宜快速的haiku、重要复杂任务用更贵更强的opus"两档（tier分层），设计初衷是省钱省算力。但因为一处参数传递的bug，所有本该走haiku的轻量任务实际全被"吞掉"路由到了opus，等于所有任务不分轻重都在用最贵最慢的模型跑，这是当时CPU占用居高不下在89%的直接原因，修复后轻量任务才真正走上便宜的模型。 |
| load  优化 | 答题一跑就顶到15.5、逼近8核机器的极限  →现在正常答题时load只有2.7-3.5 （起7个claude子进程，load仅3.5） | Load从"答题一跑就顶到15.5、逼近8核机器的极限"，降到"现在正常答题时load只有2.7-3.5"，相当于降了约77%-83%。答题/进化任务跑起来后系统负载常态在15.5左右，8核机器×2倍阈值(16)的闸门放行标准下，还没触发限流就已经很卡；进化闭环+cron全套套上负载闸门后，日常load从15.5降到10左右；`_adaptive_lane_workers`/`_heavy_slot`按load动态降并发（load<8全并发、8-15降2路、>15串行1路）后重新量的对比数字，跑GAIA错题回测时的负载已降到2.7 |
| GAIA超时率 | 60% → 30%（腰斩） | 超时率60%→30%靠的是两层兜底机制（分环节检查点+全局SIGALRM硬闹钟），保证证据收集到位后不会因为流程被强制打断而白白返空 |
| GAIA整体命中 | 38% → 47%→ 61%→72% | 38%→47%那一段（上一轮）主要靠"减少超时导致的误杀"；而47%（39%全量）→61%这一段，靠的是换了评测/答题的"模式"本身——从"pipeline机械走流程、不会主动查权威API"切换到"auto重型档，遇到源头明确的题主动调GitHub/Wikipedia/MediaWiki等结构化API去查证"，外加补齐表格解析、音频转录等工具盲区 |
