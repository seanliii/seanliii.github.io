### 第一部分：Harness 深度认知总纲

> 系列复盘的总纲与精华提炼。回答一个问题：这几个月我们到底学到了什么，未来做 harness 应该怎么走。
> 定位是**组织内技术认知沉淀**，不是面试技巧，也不是对外宣传稿。所有结论区分「已验证 / 未证明 / 已证伪」三态，事实标注出处，宁缺毋滥。

### 一、技术主线：四层演进，每一层都有边界

**先纠正一个技术起点：最早做的是我们自己的 auto，不是军团。** 前几次复盘容易把「内容、接活、社区」的产品背景放最前面，反而没把技术主线讲透。产品上我们一直追问「人有没有得到可用结果」；技术上则是四层演进：

`固定流水线 → 自研 auto 自主用工具 → 学习和连接成熟 Harness → 围绕作品持续协作`

这四个层次不是线性取代，而是**边界逐层外移**：流水线替模型预排步骤；auto 让模型自己组织工具；军团把「完整工作台」也变成可按需借用的能力，同时保住同一工程、权限和反馈。（出处：部署报告「技术主线」章节，`/tmp/meyo-report.txt` 约 1099–1119 行）

值得单独记住的是，这几个月真正留下来的不是一条「只报喜的升级曲线」，而是**六次转变**（报告约 75–100 行），每一层都对应「问题 → 动作 → 结果 → 没过关的地方」：

| 转变 | 卡在哪里 | 改了什么 | 留下什么 | 还不能说 |
| --- | --- | --- | --- | --- |
| 01 Auto 起点 | 资料越搜越多，实体认错、关系没核实 | 保留多源搜索、多跳、实体关系、反证，把题号/结果/改动放回账本 | 官方 165 题累计 162 题曾解出，98.2% | 不同轮次不能拼成同条件提分曲线 |
| 02 接着原作 | 换执行者就丢工程、忘手改 | 原文件/版本/反馈/来源交给原生执行者 | 2048 原工程加撤销，验证采用/恢复 | 有限项目旧证据，不等于所有仓库托管 |
| 03 协作生效 | 意见只存回复、原作者不续做 | 让具体观察和失败现场回到原作者 | 赛车招牌朝向、维修区有真实前后变化 | 不证明自动选优、长期群体进化 |
| 04 交付标准 | 只交会动的场景，离丰富清晰有距离 | 用旧截图和原验收检查差距 | 同单 22 天体标签和小天体粒子层 | 个案增强不等于通用世界对齐机制 |
| 05 设备动手 | 告诉用户怎么操作≠程序已运行 | 受管桌面+Redroid 里 GUI 执行、留屏幕/文件记录 | 猜数字脚本、Inkscape 原图、App 回滚 | 电脑手机不是一张全流程通过单 |
| 06 部署积累 | 部署显示成功可能只是包更新了 | 固定版本和摘要、分开依赖缓存与入口核验 | 缓存身份、安装复用、材料恢复、同包核验 | 历史证据不是当前正式全链保证 |

这六次转变的共同点，是**真正积累下来的是「组织证据的能力」**——每一层都在问「用户到底拿到了什么、怎么证明」，而不是「我们又做了什么动作」。这为后面所有认知（证伪优先、交付判据、context not control）埋下了伏笔。

#### 第 0 层：固定流水线——预排步骤是替模型思考

流水线的本质是「把人认为该走的步骤写死在代码里」。它的价值是**可复现、好观测**，但代价是——每一道题的答案和路径都被平台预先决定了，模型只是在跑一段既定的流程。

这是「context not control」这一课的最早源头：**写死在代码里的 control 是宪法病，自适应写进任务里的控制才是 harness 能力。** 我们后来反复踩的坑（固定角色、必经评审、质量门），都是这一层思维在更高维度的复发。

#### 第 1 层：自研 auto——让模型自主用工具

auto 想解决的问题是：把「模型会回答」推进到「模型能用工具把问题解决」——自主检索、读附件、运行脚本、查看中间结果，发现不对再调整。代码里的 `run_auto_agent` 是入口，`native_agent_loop` 是执行引擎。

**auto 值得留下的四类资产**（不是统统推倒）：

| 资产 | 今天的用法 |
| --- | --- |
| 自主求解的思路：目标在前，模型根据现场选工具、换策略 | 保留原生负责人的判断权，不换成更长的固定编排 |
| 真实工具资产：搜索/抓取/OCR/PDF/音视频/计算/执行 | 做成各家可发现、可调用的独立工具，不必先启动整套 auto |
| 事实/实体/关系的方法：追来源、区分同名候选、逐条件核验、保留反证 | 作为模型可用能力，不让每单都过统一裁判 |
| 连续工作的经验：上下文/检查点/失败记录/方法沉淀 | 接手者能接着做，下次实际采用有效才算进化 |

**但 auto 不能继续做「唯一总大脑」**，三条理由（出处：报告约 1139–1143 行）：

1. **单一自研引擎的维护范围越滚越大**——搜索、编程、视频、浏览器各有完整生态，每加一种能力都改同一个大内核，工具、判断、验证、收尾会纠缠。
2. **执行者擅长什么，与它能否指挥所有人是两回事**——旧方案让 auto 做过执行者、首脑、复核裁判，层层复核还可能把已经写完的答案弄丢。
3. **用户想迁移的是能力，不是被迫换习惯**——有人习惯某个编程工作台，不应先把所有人搬进 auto 的流程。

#### 第 2 层：学习和连接成熟 Harness——先证伪，再保留唯一实测有效

这一层的关键不是「接了多少家」，而是**先真跑证伪，再保留唯一实测超单家的架构**。我们证伪了六种答案聚合（v1–v6）、一致门控、topic/LLM 路由、「搜得更多」——**全部 ≤ 最强单家**。唯一真跑超单家的是**置信级联**：CC 主答 + 执行健康信号失败检测 → DeepAgents 升级，40 题 5 折 OOF 从 17/40 提到 21/40（+4，无 gold 泄漏）。（出处：`harness_baselines/meyo-orchestrator` README，34家对比文档第 97–98 行）

**这层的边界是：连接不等于增强。** 名册里登记 38 个入口，不等于 38 家在线，更不等于「人多必胜」。

#### 第 3 层：围绕作品持续协作——把「更好」变成可验证的具体变化

前两层都在回答「怎么把答案/文件做出来」，这一层回答「做出来后，下一次、下一个人、下一种设备能不能接着用」。

真正的进展只有三类（报告反复强调）：**用户新拿到一个可使用的作品；现有作品有可感知可验证的提升；真实的失败阻塞被修且原旅程重放恢复。** 纯分析、报告、测试、重构都不算进展。

这一层的标志性证据是三条可追查的旧记录（报告约 4106–4121 行）：

- **Codex → Hermes 接同一工程**：2048 工程增加撤销快捷键，作者修改与资料保留，采用/恢复有旧验收记录。
- **同伴意见被原作者真正采用**：Hermes 提只读问题，Codex 给观察，同一个 Hermes 原生会话读到完整回复后真实改文件。
- **并行确实发生，但不是两家都成功**：子 Hermes 的 README 被集成，子 Codex 未完成布局、原负责人补做。

三条都是**同 Astra 的有限旧记录**，未证明普遍胜过单家、降本或长期群体进化。

### 二、Harness 第一性认知：十条核心

#### 1. harness = 模型 + 工具 + 循环 + 记忆 + 验证的「运行装置」

模型是发动机，harness 是整车。它决定 Agent 怎么用工具、怎么循环、怎么记住上下文、怎么证明自己做了。

**引擎的价值在轨道，不在智能。** 实测 CC 只有约 1.6% 的代码是 AI 决策逻辑，98.4% 是确定性基础设施。模型的差距在缩小，harness 的差距决定体验。这解释了一个关键现象：**同一模型放在不同工作台里，能看见什么、能调用什么可能不同**——所以同用 Astra 的两家也可能补位（报告约 2583–2585 行）。

#### 2. 引擎的价值在轨道不在智能

这条是上一条的推论，但值得单独成条，因为它直接否定了「换个更强的模型就能解决一切」的幻觉。8 月上旬的方向变化就是这个认知的落地：从「再调一遍 Prompt」转向「到底哪里挡住了模型」——答案可能已经算对、最终却没交出来；材料可能已经查到、实现者却没收到。

**不能把所有失败统称为「模型不行」。** 要区分模型理解、工具环境、上下文送达、执行恢复、交付收尾五层，修复后回到原任务看结果有没有改变。

#### 3. 上下文是稀缺资源

上下文不是「越多越好」。三大技术（出处：面试宝典）：

- **结构化事实图**：我们自己的「交接冷启动」修复，把项目现场固化为 `task_memory / team_state / session / workdir` 四处持久状态。
- **WorldState 分段 + render_diff 增量**：dsh 的设计——「模型所见即已记录」由运行时不变式断言，`deriveMessages()` 从会话日志投影模型历史而非全量重发。
- **token 比例压缩**：按比例裁上下文，配合 `subagent-fork` 拆并行子任务。

**但上下文不自动保证更快更便宜。** 更大的输入、额外检索、同步、多成员协作也会增加成本。要保留完整事实、按需发送，而不是把一切塞进每次请求。

#### 4. 交接失忆：多跳推理最大的损失不在生成，在交接

自然语言传递会丢 KV cache / attention / hidden state。换一次执行者就丢工程、忘手改，用户得重新解释和搬文件——这是「接着原作」这一层转变要解决的核心痛点。

根治办法是**结构化事实图，而非失忆重跑**：换 owner 时 `_run_one_with_gateway` 的 task_facts 必须带 `project_context`（handoff/fork/revision 三处与 relay 对齐），新家从上一家的真实现场接着做，而不是空目录从零重做。

#### 5. 智能长在循环内，不是挂在循环外

核心公式：`Convergence Speed = Σ(Verification_Gain) / Time`（渐进式验证，对标 PID 控制器）。

「搜 1 次校验 1 次」优于「搜 60 次选 1 次」。三种病态模式：**搜索成瘾**（搜得多≠收敛）、**早停**（EARLY DONE）、**假完成**（部分完成说 done）。

Pilot 复盘实证：外部监控 0/10 被证伪，主动停用——因为智能要长在循环里。这条是我们后来「context not control」的前身。

#### 6. 工具即能力，工具清单如实给模型自判

Hermes Footprint Ladder 是工具接入的标准：`CLI+skill(默认) → service-gated → plugin → MCP → 新 core tool(最后)`，按足迹由轻到重，常驻清单瘦身以保护 prompt 缓存。

两个关键认知：

- **工具爆炸问题**：49 个工具 vs 2 个工具的面过宽问题——解法是把工具清单（名字+描述+来源+能力）如实给模型让它自己判断，不写正则枚举。
- **万物皆插件**（dsh）：插件生态是广度，工具收敛是深度。军团的 adapters 目前是手写接入、不是声明式插件树，这是诚实承认的差距。

#### 7. 记忆要有消费者

记忆的坑不在「存」，在「存了没人用」。四层架构：Session → Effective → Topic Summary → Persona；短中长三档 + 并行召回 + Reranker + 配额管理。

**「写了一份记忆不等于学会」。** 我们的判据是：下一次任务真的用上并产生净收益，才叫进化。`_recall_experience` 注入时标明「仅供参考」，由模型自己判断用不用；`adopted` 采纳票提置信度、`prune` 淘汰没人采纳的。

#### 8. 设备层扩展交付面

Agent 的边界从「文字答案」扩展到「真实设备上的业务状态」：

- 云电脑（Linux 桌面容器 + noVNC）：操作真实桌面（终端/IDE/浏览器/拖拽）并截图取证。
- 云手机（Android）：生活 App 业务状态交付（商店→安装→注册→跨 App）。
- 任务状态机：`needs_software→needs_account→ready→running→needs_confirmation→done/partial/blocked`，每步可断点续跑。

意义：把「一句话」变成可打开、可操作、可部署的唯一主成品，而不只是文字。这是 34 家里几乎没有的「最后一公里」。

#### 9. 诚实证伪：正负结果一起发表

这是我们从血泪里长出的最值钱的方法论。**走通一条 > 证伪十条。** 已证伪的死路（真跑证明无效，再提直接拦）：多家答案 post-hoc 聚合/融合、一致门控/投票、topic/LLM 路由、靠「搜得更多」提分、加治理门/兜底/二模型否决「保证质量」、用报告/JSON/截图/测试代替用户得到好成品。

**负结果也要发表**：11 错题自进化 0 救回、组队 v1/v2/v3=4/4/2 低于最强单家 5/10、四臂 A/B 输了照写进设计约束——这些比任何吹牛都有杀伤力。

#### 10. 成本约束：量大管饱不等于无限免费

「更便宜」不是营销口号。W28 自述并行竞争和真实执行让成本明显上升、产量下降，质量改善还是自评。真正的比较口径是：**所有失败尝试、工具、推理、存储、人工救场成本 ÷ 合格交付数**，而不是单次 token 单价。

单次模型单价低，不等于最后一件合格成果便宜；边际费用下降，也不等于项目总预算下降。

### 三、架构认知：平台底座应该提供什么、不应该提供什么

这是「context not control」在架构层的落地。一句话：**Meyo 是运行系统，不是新 Agent；是 Harness 的运行底座，不是上方另造的答题器或质量裁判。**

#### 应该提供（安全/运行边界可以硬）

| 平台职责 | 具体内容 | 为什么必须平台做 |
| --- | --- | --- |
| **现场继承** | 原工程、版本、来源、失败、下一处缺口整体移交 | 换 owner 不失忆，减少重做 |
| **工具可发现** | 标明来源/path/runnable，调用前检查依赖 | 「在目录不等于可用」，让执行者找得到、用得对 |
| **证据组织** | 关键动作、来源、文件差异、版本、时间、成本可查 | 让用户能回答「读了什么、改了哪里、依据是什么」 |
| **失败回流** | 完整失败回执回到原负责人 | 让真实失败可消费，不靠外层替它写答案 |

一句话：**接现场、保事实、让反馈回到正确执行者、缺工具时能借能力，并把下一步决定权留给原生助手。**

#### 不应该提供（产品质量策略必须软）

| 不该做的 | 为什么错 | 我们的替代 |
| --- | --- | --- |
| 替模型写步骤 | 写死的 control 是宪法病，换品类就废 | 任务文本每单自适应生成 |
| 统一裁判/质量门 | 把模型已写出的答案弄丢；制造 empty_final | 并列事实，不做上帝总判决 |
| 一致门控/投票 | 弱家一起给同一个幻觉，一致≠正确 | 单一最强家 + 严格 abstain |
| 把 auto 的强裁决整包复制 | 层层复核把已完成答案弄丢 | 验证变成搜索，不是打分 |

**核心区分原则：** 看见 `gate/contract/auditor/verdict/threshold` 先分类——是安全/运行门，还是替 Harness 决定任务质量？后者必须改成 Context。正确数据模型是并列事实（`harness_result / runtime / artifact_observations / peer_review / release_evidence`），不做上帝总判决。

一个具体反例（报告约 1138 行）：旧「校验即搜索」模块确有主动找反例的实现，但也含固定查询模板和阈值——不能整包复制成军团的默认质量门。**资产必做 = context 必做，不是验收必做。**

#### context not control 在代码里的三个落点

这条不是口号，有三处可查的代码落点（34家对比文档「我们的异化」章节）：

1. `**_record_experience**`** / **`**_recall_experience**`：只记事实不评判，注入时标明「仅供参考不一定对」，采纳与否由 harness 自己回报（`legion_tool.py adopted`）。这是「记忆有消费者、父层不猜」的实现。
2. `**_is_delivered**`：明确「不要用『至少 20 字』之类规则替模型判断答案质量」。只把占位词（UNKNOWN/NONE/N/A/null/未完成/无）判为「明确的无内容声明」触发熔断——**短≠空**。
3. **ADR-005 全模型自主编排**：删光硬编码路由，只留客观工具（list_harnesses/read_history/read_trace/run），模型 3/3 自主选对性价比最优家。

**「短≠空」是交付判据的底线**，也是最贴近用户结果的一条：合法短答（「2」「好」）就是真交付，长度从来不是质量判据。这是对「用测试数/文件数冒充进展」的系统性抵抗。

### 四、评测认知：分数是不是真的

#### 1. 评测的第一个问题不是题目好不好，是分数是不是真的

gold 泄漏审计四步 + 双轨评测集 + 独立集交叉验证。三个层次不可混用（面试宝典）：

| 层次 | 测什么 | 用途 |
| --- | --- | --- |
| 公开榜（Artificial Analysis） | 底座能力 | 选模型 |
| 可运行题库（GAIA） | 端到端 | 发布级验证 |
| 盲评（Head-to-Head） | 用户偏好 | 产品决策 |

#### 2. 口径纪律：历史账本的 14 个口径

部署报告专门列了 14 个评测口径，核心教训是**「曾经会」≠「稳定会」**：

- **162/165 = 98.2% 是「累计曾解出率」**，不是单次无污染成绩，不同轮次与输入条件不能拼成同条件提分曲线。
- **61% 是「旧通过题 + 新救回题」的合并口径**，不是 auto 在 165 题上统一条件的首过率。
- **BC20 摘要 16/20、逐条 17/20**——两类布尔标记定义不同，不能相加。
- **164 累计峰值后来撤回 3 道污染假胜，改报 161**。

**旧数字不连成一条提分曲线。** 累计最好、定向救题、不同模型预算、格式问题、真实错误混在一起，会让数字看起来进步却解释不了稳定性。

#### 3. 双轨评测：回归题与真实 Query 分开

历史/模型题只标 `regression | synthetic_stress`，不能证明用户价值。大考的 Query 依次来自：当前用户原话 → 真实 session 的 failed/partial/返工/继续追问 → 被接受/编辑/复用且可能形成长板的 Query → 明确 owner 带真实输入的 dogfood。

「好/4/7」等短答回归仅作廉价回归，绝不冒充上线。

#### 4. 负结果也要发表

评测用来暴露短板，不能代替真实交付。关键负例必须保留：

- **11 错题自进化 0 救回**——证明「有记忆 ≠ 群体进化」。
- **组队 v1/v2/v3=4/4/2 vs 最强单家 5/10**——明确反对「人多就好」。
- **视频小样本改变了抓取路径，4 道视频题最终仍未答对**——流程更合理不等于正确性提高。

#### 5. 失败形态：先修输入，不急着判「模型不行」

旧 100 道错题的四类去向（36 救回 / 26 作答仍错 / 8 超时 / 30 缺附件跳过）拆出了五种不同的失败形态（报告约 7138–7168 行），这是评测认知里最实用的操作指南：

1. **原件没到手**：题目指定了表格/PDF/图片/视频，系统却拿不到原件，搜出来的「相似资料」不是替代品。旧 100 错题里 30 道因缺附件跳过，证明的是当时输入链缺口。**补齐输入有价值，但不保证原题会答对。**
2. **搜到却不对**：搜索蜂群不是「越多越强」。结果可能不贴题、来源互相冲突、最后一跳没有支持证据，甚至资料找到了却没被后续执行采用。工具数量是可用选项，有效答案才是结果。
3. **做了仍答错**：26 道提交了错误答案，但缺统一逐题根因。视觉识别、条件理解、算术、多跳推理可能分别出错。一个尤其重要的负例：旧视频小样本改变了抓取路径，4 道视频题最终仍未答对——**流程更合理不等于正确性提高。**
4. **实体关系串错**：缺的可能是最后一跳，而不是下一百条搜索。一条人物题虽积累 14 条证据，候选中却混入了搜索服务名称。资料多不等于主体识别正确。
5. **过程丢了交付**：超时、撞步骤上限、结果字段漏读、异常收尾、恢复断链——各自要不同修法。「工程失败」不等于「只要修工程就会答对」。

这五类的共同结论是：**Meyo 应做的是让任何一家都看得见自己的处境、拿得到已有文件、可继续执行；不是在上方替它决定答案。** 每一类失败先归因到「模型理解 / 工具环境 / 上下文送达 / 执行恢复 / 交付收尾」这五层之一，再谈怎么修。

#### 6. 为什么评测不错，作品还是可能不好用

这是评测认知里最反直觉的一条（报告约 7225–7229 行）：**答对一道问题、把文件写出来、作品达到专业水平，是三种不同的结果。**

评测让我们发现资料、工具、记账和收尾的问题；真实作品又会暴露画面、交互、玩法、声音、持续修改和协作的缺口。所以：

- 不能把 GAIA 分数搬到赛车上，声称赛车也世界级；
- 不能用一个很好看的截图证明所有机制有效；
- 评测用来暴露短板，不能代替真实交付，更不能证明社区复用与留存已经成立。

**六项世界级目标（游戏/视频/网站/报告/搜索/速度）是六种交付要求，不是六个口号**，也不是同时开六条研发线的理由。已知水平与缺口都要如实标注：赛车有真实改善但手感/音效/手机/耗时未证顶尖；视频找回了成片但文件完整 ≠ 叙事审美世界级已验。

### 五、组织认知：军团到底是什么组织

#### 1. 38 入口不是 38 家在线

名册是 9 月 29 日源码快照（报告约 3978–4013 行）：**38 个登记入口 = 内置 10 + 外接 28**，按角色分：执行角色 28、工具/能力 7、控制平台 2、桌面平台 1。

内置执行入口只有 9 个：Claude Code、Codex、Hermes、DeepSeek Harness、DeepAgents、JCode、Penguin、Prime、Omnigent。第 10 个内置条目是 **Auto 工具库**——引擎停用，不进答题、接力、首脑池。

几个容易混的账：

- prime ↔ prime-intellect 是兼容转接，**不算两家**独立 Prime。
- penguin ↔ penguin-harness 同源，入口/配置/运行版本要分别核。
- Omnigent ≠ OmniAgent，不能因名字相近合并。
- 「在目录不等于可用」：依赖、平台、权限、工具、原目录、会话都要成立，工具能力和控制平台**不应混进答题池**。

#### 2. 单家优先，真缺口再补位

组织的第一原则不是「让很多人参与」，而是：

> **先把最强单家的原生能力用足，确有缺口再借工具、借完整工作台或请同伴补位。一家已经最优，就让一家做。**

「单家一定做不好」不是立项前提。个案失败只证明这次没做好，不能直接证明单家先天不行——应先排除工具、上下文、环境和恢复故障，再看跨工作台合作是否有不可替代的增益。（报告约 2586–2589 行）

#### 3. 五种职责、六种配合

**五种职责**（不是每单强制走五道工序）：

| 职责 | 衔接 | 不能误解成 |
| --- | --- | --- |
| 计划提出 | 模型读取目标/附件/候选/能力状态，返回任务与关系 | 平台已知道唯一最佳答案 |
| 负责人选择 | 用户指定、候选条件、静态偏好、历史信号、提案评分共同作用 | 38 家全体开会、全生态最优 |
| 运行执行 | 调度器管理依赖/绑定/租约/取消/工作目录/状态 | 调度成功 = 作品完成 |
| 原生工作 | 负责人用自己的工具做事，遇缺口求助或交接 | 固定品牌只能做某职业 |
| 最终收口 | 原作者核同伴结果、读差异、改文件、交付 | 平台投票拼答案 |

**六种配合**（不是一回事）：单家直接做 / `need_peer` 请教 / `handoff` 交接 / `fork` 并行 / 失败接力 / 同题比较。

#### 4. 组队不保证胜过单家——这条必须钉死

**旧 10 题自述：组队 v1/v2/v3 为 4/4/2，最强单家为 5/10。** 不是当前排名，但不支持「人多必胜」。

三条协作个案也没有同条件最强单家对照与完整费用对照。能力借用旧记录里，上下文/JSON 传递修过、子原生也启动，但沙箱返回 `Operation not permitted (71)`，指定文件读取未证、原作品没改——**outer ok/done 不能当工具成功**。

所以「群体超过单家」是**要验证的目标**，不是因为接入更多成员就已经成立的事实。产品之魂三内核（群体互相进化 / 最强全部为我用 / 智能远超单家）是尺子，不是已经达成的成绩。

#### 5. 为什么要保留差异，而不是统一成一种 Agent

这是军团区别于「再造一个 agent」的根本：**家是工作台，模型是它使用的「大脑」。** 同一 Astra 可以被不同 Harness 使用，区别还在原生工具、文件工作方式、会话、插件、上下文处理与恢复协议。

保留差异是为了四件事（报告约 4059–4065 行）：

- **保留原生工作方式**：不把各家削成同一个聊天接口，才有机会复用它们的原生长处（CC 的 `--resume` 会话、Codex 的 thread/exec、Hermes 的 AIAgent history、dsh 的 persistence bridge、DeepAgents 的 SqliteSaver 图 checkpoint）。
- **共享同一项目现场**：接手者知道目标、文件、版本、来源和失败，减少搬运与重做。
- **让原作者真正消费帮助**：同伴回复不是成品，必须回到原任务、发生实际修改或明确取舍。
- **并行有独立写面和收口者**：共同基线、分离副本、固定差异，再由原负责人集成，避免互相覆盖。

**诚实承认我们的差距**（34家对比文档「诚实说我们没有的」）：dsh 的插件生态广度与「零特权内核」的可组合性我们不及（adapters 是手写接入）；codex 的短循环极简让单题直答速度上我们要多一层编排成本；hermes 的用户长期画像（Honcho 辩证建模）比我们的经验飞轮更深。承认差距，并把 dsh/codex 的架构点吸收为已验证的正向杠杆，而不是宣称全面超越。

#### 6. 七条有源码支撑的异化

我们的差异点不是「又造了一个 agent」，而是**造了一台让世界最强 harness 互相看见、互相接力的运行系统**（34家对比文档「我们的异化」）：

1. **交接冷启动**：结构化事实图（`task_memory/team_state/session/workdir`），而非失忆重跑。
2. **Verification-as-Search**：Critic 主动搜反例做四态裁决，把验证嵌进解题循环。
3. **context not control**：安全边界硬、质量策略软，并列事实不做上帝总判决。
4. **证伪四方案后的置信级联**：只保留唯一实测超单家的架构。
5. **经验飞轮（跨家记忆）**：codex 这次答的，cc 下次 search 能看到，且按 user 隔离。
6. **云真机设备层**：把交付推进到真实软件/业务状态。
7. **交付判据「短≠空」**：长度从来不是质量判据。

**异化的本质一句话收束**：34 家里 codex/deepseek/hermes/penguin 都在「把单个 agent 做深」——短循环、插件化、学习环、自进化；而军团回答的是另一个问题——**当世界已经有一群最强 harness，如何让它们为一个用户的意图协同工作、且用户不用知道复杂。** 所以军团的每个机制都是「群体协作与交付可靠性」的增量，而非「再优化一个单 agent」。

### 六、下一步验证清单：跟住一条真实任务，记录全成本，净改善才推广

报告结尾收敛成一句核心思路（报告约 4135 行）：

> **跟住一条已获准的真实任务，记录实际成员和模型、计划变更、工具、原文件变化、失败与全部成本。只在结果、可靠性或管理负担出现净改善时，才把方法继续推广。不能为了凑名单或给报告提分新跑一轮。**

#### 要证明的两件事

| 目标 | 正确的比较方式 | 不能偷换成 |
| --- | --- | --- |
| 把质量上限推高 | 同一真实需求，最强单家用足工具和原生协作；再比较额外补位是否让成品更好，正确性与核心可用性不退化 | 多家参与、长回复、源码量、漂亮截图 |
| 同等质量更便宜 | 小模型+好工具+已有作品+有效方法 vs 原方案；全部失败/工具/推理/存储/人工救场成本都算 | 单次模型单价低 |

#### 建议的验证标准（是建议标准，不是已有成绩）

- **稳定交付**：20 条不同真实需求（网页/小游戏各 10），≥18 条完成核心用途与保存恢复，≥16 条无需工程师代改/搬文件。不达标→修原旅程，不拓量。
- **协作净收益**：10 对完整能力最强单家 vs 按需协作，同输入/资源/预算，≥7 对在两项按任务事先确定的关键维度胜出、正确性与可用性不退化。**7/10 只作本批加码信号，不是普遍优势。**
- **同质量更省**：每件合格交付的全部推理/工具/失败重试边际费用下降 ≥30%，成功率不降，总耗时不恶化超 10%。
- **经验真进化**：≥5 条不同的真实后续任务实际采用已有方法，逐条记录采用点、原作者和差异。只出现 Skill 记录、未采用或难归因，标未证明。
- **用户回来**：激活 ≥40%，D7 有效回访 ≥20%、D30 ≥10%，≥20% 激活用户实际采用他人作品派生版。

#### 判据底线

**技术成立但没人回来，就调整场景；协作不划算，就保留单家。** 证据过线，再扩大投入。

对应到每一天的执行：默认循环是「恢复原始 Query/现场 → 立即做 Wonder Slice/首版真成品 → 最小相关验证一次 → 真用户旅程 → 最大 Gap 返工」。只有当前交付已撞到且有源码+运行证据的底层阻断才最小可逆修复，修完立即重放原旅程。

#### 从 query 到交付的可靠性底线

验证清单要成立，还依赖四条已被证明有效的可靠性底线（34家对比文档「已验证正向杠杆」）：

1. **杀前落盘**：结果先写盘再退出，进程被强杀也不丢。
2. **收尾预算隔离**：给收尾留独立预算，不因主任务超时把已写出的答案吞掉。
3. **空答案熔断**：占位词（UNKNOWN/NONE/未完成）触发熔断，不当交付。
4. **补位接力**：一家用尽 attempt 仍失败 → task + 完整失败 context 转交另一家接力（带旧 context 不是失忆重跑）。

这四条的共性，是把「交付可靠性」从「模型别出错」还原成「系统别把模型已经做出来的东西弄丢」。它们与「短≠空」判据一起，构成了验证清单的底层地基——**先保证「做出来的能被用户拿到」，再谈「做得更好、更省」。**

### 结语：一次只集中做一件

这几个月真正值得留下的，不是 38 家的名册，也不是 162/165 的累计账，而是**把动作量和进展分开**的能力：产品任务以「新真成品 / 可感知提升 / 原失败旅程恢复」为基线；机制提分或修复才要求同输入旧结果→重跑新结果→Δ。

未来做 harness 的完整认知框架，浓缩成一句话：

> **模型是发动机，harness 是轨道；平台只接现场、保事实、让反馈回流，不做上帝裁判；先让最强单家用足本事，真缺口再补位；跟住一条真实任务记全成本，净改善才推广。**

已证明的，守住；未证明的，诚实标注；已证伪的，写进黑名单不再碰。这就是世界级质量驱动的唯一正道。

### 一、项目全景

#### 1.1 军团是什么：一句话说清定位

军团不是「又一个 agent」，也不是「一个更好的答题器」。它的定位是：**当世界已经存在一群各自最强的 harness（Claude Code / Codex / DeepSeek Harness / Hermes / Penguin / Prime……），如何让它们为一个用户的真实意图协同工作，并且用户完全不需要知道背后的复杂。**

这个定位的源头是「产品之魂三内核」：① 群体互相进化（读彼此源码、召回经验、补位接力，涌现智能 > Σ 单家）；② 最强 harness 全部为用户工作（复杂性对用户透明，强大可感）；③ 直观智能远超单家（首脑组织 + 深度协作 + 工具工厂 + 自进化）。

用一句更工程的话收束：34 家里，codex / deepseek / hermes / penguin 都在「把单个 agent 做深」——短循环、插件化、学习环、自进化；军团回答的是另一个问题——**「运行系统 + 事实底座」**，不替它们解题，只补上下文、工具、失败回流、完成契约。这条边界在源码头注释里写死了（`legion_core.py:3-13`）：

```
// 代码块
"""军团内核 (legion_core) —— 薄封装 · 给模型 context 不加 control
...
  - 军团 = 一群可并行调度的 harness(...共10家真harness)。cua/supervision/herdr/orca 是【能力后端】不是
    harness(桌面/CV/终端/并行编排)·归工具能力·不进派单池(2026-08-28 定位纠正)。
  - 不做已证伪死路:不强制融合各家答案、不投票门控、不 topic 路由。
    只把各家原始结果并列呈现,控制权交用户(选谁最强/继续谁)。
```

它直接承接 auto 项目 8.22–8.24 的「六家对标」结论，并留下了两个关键输入——「保留独立推理路线再仲裁，不搞全家桶证据池」。军团不是再造一个答题器，而是把这些 harness 编成「给 C 端的 Agent 团队即服务」。

#### 1.2 演进时间线：三天半敢交付，之后一直在「证伪—收口—再证伪」

### 二、核心认知提炼（每条 = 当时问题 → 实验 → 结论 → 代码落点）

这一章是复盘的主体。每一条都是一次真实踩坑后钉进源码或文档的结论，不是事后归纳。

#### 认知 1：多家放一起，不自动更强（8.26 六种聚合架构全灭）

**问题**：立项次日最该回答的问题是「多家组队到底值不值」。直觉答案是「值」，三个臭皮匠。

**实验**：真跑证伪了六种答案聚合架构（答案选择 / 约束核验 / 证据级聚合 / 分歧重搜 / 逐一反证 / 矩阵），全部 ≤ 最强单家。队长 v1–v6 的实测成绩是 4/4/2/0/2/0，而最强单家是 5/10——不是差一点，是系统性全灭。

**结论**：**post-hoc 聚合/融合/投票在真实数据下全低于最强单家**。这进了「已证伪死路黑名单」，成为军团永远的禁区。

**代码落点**：`legion_core.py:3-13` 头部注释明确「不做已证伪死路：不强制融合各家答案、不投票门控、不 topic 路由，只把各家原始结果并列呈现，控制权交用户」。这条不是嘴上说说，是写进了内核的第一行设计哲学。

#### 认知 2：一致 ≠ 正确（一致性门控被判死刑）

**实验**：弱家一致时是「一起给同一个幻觉」。deepseek + hermes 一致时 11 题全错（0 对），一致门控精度 0%。

**结论**：**一致性是幻觉的放大器，不是质量的保证**。这条路彻底关闭。直觉上「大家都同意 = 对」，但真实数据证明：弱家一起给同一个幻觉时，一致反而是最危险的信号。

#### 认知 3：搜得多 ≠ 对（搜得多 = 卡住空转）

**实验**（GAIA 40 题三方对照，日报 2783290420）：

| 指标 | codex | deepseek | auto |
| --- | --- | --- | --- |
| 命中 | **33/40** | 19/40 | 22/40 |
| 空答案 | **0** | 1 | 12⚠️ |
| 崩溃 | **0** | 0 | 多个⚠️ |
| 均耗时 | **167s** | 310s | 510s |
| 均搜索 | 6.6 | 1.0 | 13.4 |

最反直觉的发现：codex 赢**不在「搜得多」**（它搜 6.6 次，auto 搜 13.4 次），而在「100% 交付 + 0 崩溃 + 快 3 倍」。auto 搜得最多却有 12 题交空白；而且 auto **未命中题搜得更多**（10 次/45 步 vs 命中题 6.5 次/31 步）——卡住时 thrash 空转，不是收敛。

**结论**：优化方向是「信息增益驱动的早停 + 上下文压缩 + 收敛优先于穷尽」，而不是加搜索预算。

#### 认知 4：加治理门 = 制造 empty_final（把模型已写出的答案弄丢）

**实验**（日报 2783142110）：加治理门 / 兜底 / 二模型否决「保证质量」，结果是 `final_authored_but_lost` 11 题——模型已经写好的答案被门给丢了。

**结论**：**加门 = 制造空卷**。这是对「在 harness 上方另造质量裁判」最直接的证伪。产品质量策略必须软，安全运行边界才可以硬。

#### 认知 5：唯一实测超单家的是置信级联（17→21/40）

**实验**：CC 主答 → 读取运行时健康信号（search_count/elapsed/final_len/timeout，**不用 gold、不读题型关键词、不投票**）→ Logistic 级联决定是否升级到 DeepAgents。BC 40 题 5 折 OOF 从 17/40 提到 21/40（+4，无 gold 泄漏）。

**结论**：这是军团「A/B 必须带来真性能提升」目标下**少数有数据的正向机制**。它同时定义了军团的编排哲学：**先证伪、后保留唯一实测有效的架构**。`harness_baselines/meyo-orchestrator/` 的 README 就是这个结论的源码源头——「值钱的是把各有脾气的开源 harness 稳定串起来」，只给模型 15 个客观工具（list/stats/history/trace/run/probe/judge/self_evolve），模型自主决定派谁、并行、交叉验证、何时停。

#### 认知 6：家是工作台，模型是它使用的大脑（原生工作台价值）

**问题**：为什么不把 34 家全部削成一个统一的聊天接口，方便管理？

**结论**：不同 harness 的原生工具、文件工作方式、会话、插件、上下文处理与恢复协议是它们的价值所在。同一模型（比如 Astra）可以被不同 harness 使用，区别还在原生工具、文件、会话、插件、上下文处理与恢复协议。保留差异是为了「少重做、能补位」，不是把品牌写成固定职业或实力排行。

**代码落点**：每家 adapter 各自保留原生 resume 协议——Codex 用 `codex exec resume <thread_id>`（`harness_registry.py:2131-2137`）、Claude Code 用 `--resume <session_id>`（`:1677-1695`）、Penguin 用 `chat --resume`（`:3064`）、Prime 用原生 `prime_jsonl_v3` 会话格式（`external_adapters/prime_native.py:16`）。**注意代价**：CC 的 `--bare` 会跳过 hooks/插件/自动记忆，不是所有原生扩展都原样启用——保留差异是有取舍的，要诚实。

#### 认知 7：同一工程现场，是「补位」比「换更强的家」更本质的地方

**问题**：多数 harness 换模型/换会话即掉记忆，接力等于失忆重跑。

**结论**：军团把「项目现场」固化为 `task_memory / team_state / session / workdir` 四处持久状态（AGENTS.md 定为唯一权威源）。换 owner 时 `_run_one_with_gateway` 的 task_facts 必须带 `project_context`，新家从上一家的**真实现场**接着做，而不是空目录从零重做。

**代码落点**：`project_context.py:139-162` 的 `_initialize_locked`——「合并原有项目事实，不另建执行现场」，同会话继承 `decisions/completed/open_gaps/verification_findings/artifacts/attempts/repo_root/workspace_root` 等；`legion_core.py:6620-6644` 构造 `TaskFacts` 时 `project_context=_project_snapshot`。这是「交接冷启动：结构化事实图，而非失忆重跑」的源码本体。

#### 认知 8：交付判据「短 ≠ 空」（删掉「至少 20 字」长度门）

**问题**：防止交白卷，直觉是加长度门槛（「至少 20 字」）。

**结论**：长度是「量」不是「质」。合法短答案「2」「好」就是完整交付，父层拿长度误杀会触发接力 = control，违反「给 context 不加 control」。唯一例外是**事实门**：final 是占位词（UNKNOWN/NONE/N/A/null/未完成/无）才是「明确的无内容声明」，触发熔断。

**代码落点**：`_is_delivered`（`legion_core.py:4945-4960`）只信 run_one 的客观结果，`status=done + final 非空 + final 非占位词`。配套 `_typed_outcome`（`:4963`）把「这单完成没有」从四处各自判断归一成 completed/partial/failed/incomplete/cancelled/blocked 的结构化投影，对齐 codex 的 `ThreadShutdownReport` 分类收集思想。

#### 认知 9：能力借用未闭环——「借到入口 ≠ 工具执行成功」（71 错误）

**问题**：把 auto 的工具源码暴露给 harness，等于「能力借用了」吗？

**实验**：旧能力借用修过上下文与 JSON 传递，子原生也启动了，但**沙箱返回 **`**Operation not permitted (71)**`，指定文件读取未证，原作品未改。

**结论**：不能把 outer ok/done 包装成能力借用完成，更不能绕过沙箱把失败改成成功。`capstack_bridge.py:115-139` 的 `call()` 保留 `runnable: False` 与失败回执，参考源码不自动成为工具。

#### 认知 10：诚实证伪方法论——「走通一条 > 证伪十条，根因优先」

**结论**：军团不是从零猜架构，而是先真跑证伪六种聚合/门控/路由/「搜得更多」，只留唯一实测有效的置信级联。这把每一次编排都站在被证伪的尸骨上，而不是堆仪式化评测。这条方法论是整个项目最值得组织内复用的资产。

#### 认知 11：context not control——召回是半环，父层绝不猜「用没用」

**问题**：经验飞轮召回历史经验后，父层如何判断它生效了？

**结论**：**只有 harness 自己知道哪条经验真被采纳了**，父层替它宣称「参考了/辅助了本次回答」是典型的「在 harness 上方另造质量裁判」。所以 `_recall_experience` 只注入「找到 N 条历史经验供参考」的事实，并给模型一个 `legion_tool.py adopted "<Q原文>"` 的真回报入口——好经验靠真实采纳票浮上来，没人采纳的 prune 淘汰。

**代码落点**：`_recall_experience`（`legion_core.py:9905-9939`）——「只报『注入了什么·供参考』，效果由军团自己决定」；`_record_experience`（`:9863`）只记事实不评判，且按 `user_id` 隔离（`legion_memory.add(user_id=)`，修掉了跨用户记忆串的隐私风险）。

#### 认知 12：交付可靠性三件套——杀前落盘 / 收尾预算隔离 / 空答案熔断

**结论**：「编排协议 done」不等于「用户真拿到交付物」。codex 交付最稳的根因就在架构：错误被 catch 成结构化事件、收尾在 finally 必然执行、中断抢救半成品，因此「没有跑很久交空白/进程猝死」的形态（日报 2783290420）。军团把它吸收为三条可靠性底线。

#### 认知 13：模型选择靠真实战绩，不靠一次性测试（Wilson 95% 下界）

**结论**：数据源是每单自动落账的 `model_health.json`（`record_model_health` 只记可归因失败——gateway/rate_limit/provider/model_config/truncated/empty；环境/Harness/工具/用户失败不记模型坏账，避免环境病污染排名）。打分用 Wilson 95% 下界，**小样本不虚高**，1 次成功不会顶掉 100 次验证过的老模型。

这条背后还有两段硬核实测（模型对比文档）：

- **六家 5 题 BrowseComp 对照**（日报 2782515730，同 gpt-5.6-sol·temp=0·同 SearchFabric·1200s 墙钟）：DeepSeek 3/5 靠事件溯源 + source anchor 坚持（Eldorado 题唯一命中）；Codex 2/5 但 **4/5 零搜索直猜**——低延迟 ≠ 检索最强，是「赌模型先验」；Auto 2/5 = 功能最多、可观测最低、治理层最多。
- **裸 CC 快的真相**（日报 2779137315，GAIA 9 题）：裸 CC 2/9，觅游（qa∪auto）5/9 是裸 CC 的 2.5 倍。裸 CC 快不是模型更强，而是 `claude --print --model opus` 自带 Claude Code 内置 WebSearch（60-150s 轻量云端搜），答对的全是名人常识，答错的题它也快（18-48s）因为直接放弃。

**代码落点**：`select_usable_model`（`legion_core.py:10420`）——trusted_appids 白名单优先、跳过 known_broken_models + quota_exhausted_appids、同请求失败后 `exclude_models` 保证真换模型、per-harness 健康重排、appid 轮换起点用全进程单调游标错开并发。这是「context not control」在模型层的落地。

#### 认知 14：能运行 ≠ 质量好（3D 对战泛白案例的分层）

**问题**：接力成功（CC 接到了原工程），作品质量就一定变好吗？

**结论**：**机制成功与作品质量是两层**。3D 对战案例里，CC 接到同一工程后画面反而泛白（旧记录 926 → 8d41），「能运行不等于更好看」。这是「换了原生工作台，也不是原 Hermes 同一 native SID」的真实证据——运行机制的可靠性和交付物的质量必须分开验证。

#### 认知 15：最新 ≠ 最好（8406 新资产退化，保留 6f 基线）

**结论**：3D 对战案例里，尝试引入新 GLB/解析/动画绑定的 8406 版本，实测「出生/复活实体没画出」，于是**不因文件较新就自动替换默认体验版**，保留 6f2381e8 基线，8406 只作为失败证据。这是对「用文件新/文件多冒充进展」的直接抵抗，也是版本管理纪律的雏形。

#### 认知 16：派单池纯净性——capability 家永不进答题池

**结论**：capability/control-plane/ui-platform 家不是答题家，一旦混入答题池就是脏数据（browser-use 0/51 脏账实证）。任何 catalog 结果收集成 key 集合的派单消费点必须过 `_answer_keys_from_catalog`。

**代码落点**：`_NON_ANSWER_ROLES = ("capability", "control-plane", "ui-platform")`（`legion_core.py:314`）、`_answer_keys_from_catalog`（`:316`），回归锁 `tests/test_dispatch_pool_guards.py`。

#### 认知 17：环境失败 ≠ 模型失败（自愈要换的是环境，不是模型）

**结论**：hook 拦/连接拒/rc-9/rc143 是环境失败，修环境或降级绕开，不是换模型重试；cc 用官方 `--bare`，子进程传 NO_PROXY。`_build_failure_context`（`legion_core.py:2033`）区分「环境失败 vs 模型失败」，这是「不把环境病当模型病治」的源码落点，也是反复踩坑后钉下的方法论。

#### 认知 18：从世界最强 harness 学架构，而不是闭门造车

军团有三个被明确标注为「已验证正向杠杆」的架构借鉴，全部来自读真源码（`harness_baselines/` 目录）：

- **codex 的 final schema + 先验直答 + 单次检索确认**：极短循环，绝不「搜得更多」空转。军团把它借进 `_typed_outcome` 的 ThreadShutdownReport 分类收集思想。
- **dsh 的 WorldState 分段 + render_diff 增量 + token 比例压缩**：会话日志是「模型所见上下文的唯一来源」，`deriveMessages()` 从状态投影模型历史而非全量重发。这是军团上下文压缩的直接参照。
- **hermes 的 Footprint Ladder**：`CLI+skill(默认) → service-gated → plugin → MCP → 新 core tool(最后)`，按足迹由轻到重接入、常驻清单瘦身以保护 prompt 缓存。军团仿了它的 `RecallStatus` 透明召回。

**结论**：成熟开源实现先核许可/活跃度/质量，优先合法 reuse/extend/组合，不从零造低质替代品也不盲抄。这是「站在被证伪的尸骨上 + 站在巨人的肩膀上」两条腿走路的完整方法论。

### 三、代码架构详解

#### 3.1 调度中枢 `legion_core.py`（~10700 行）

对外只暴露三个函数（`legion_core.py:15-18`）：`list_harnesses()`（客观列出全部成员，无排序/推荐）、`dispatch(question, plan, cb)`（一句话派活并行执行）、`run_one(key, task, qhash)`（单独派一家）。这是「薄封装」的第一层：**内核不背答题逻辑，只做调度与事实底座**。

关键函数与设计决策：

- `**_ORCH_CANDIDATES**`**（:44-56）**：定位 `meyo-orchestrator` 编排层，按「环境变量 → 打包布局 → 仓库内布局」三路径查找，兼容开发与分发两种形态。

- `**_answer_keys_from_catalog**`**（:316）+ **`**_NON_ANSWER_ROLES**`**（:314）**：派单池纯净性的第一道闸。任何 catalog 收集成 key 集合的派单消费点必须过它。

- `**elect_captain**`**（:429）+ **`**_bid_strength**`**（:726）+ **`**_pref_order**`**（:369）**：首脑竞选的现实是「混合机制」——模型提出计划，候选/用户偏好/静态排序/运行条件共同参与，`winner = max(eligible, key=_bid_strength)`（:759）按方案完整度选，不是全生态自由盲选。这里有个重要的源码级纠偏（:363-368 注释）：`_pref_order` 曾经被当过滤器（`base=[k for k in _pref_order ...]`），导致 cline/goose 等 `_pref_order` 外的新家永远进不了候选——这就是「为啥体验不是 20 多家」的根因。修复后 `_pref_order` 降级为「已验证快家的排序提示」，只决定谁先抢答，不再当过滤器，池外新家按 `cost_class` 排后面仍能参选。**这个 bug 的教训是：把「排序提示」和「准入过滤器」混用，会静默地杀掉全部新成员。**

- `**run_one**`**（:3113）自愈换模型循环**：单家执行的兜底循环——首轮带 appid，失败真换模型/provider、方向归一、codex 错误回流、剥 think 草稿。配合 `_GatewayLease` 按 cost_class 分级控并发，`_build_failure_context`（:2033）区分环境失败 vs 模型失败，`_MAX_ATTEMPTS`（:1345，默认 0）控制重试轮数（每轮硬墙钟，超时如实回流让 harness 自主换招，不父层一刀切杀）。

- `**_is_delivered**`**（:4945）+ **`**_typed_outcome**`**（:4963）**：交付判据与 typed 单一事实源（见认知 8）。

- `**_pick_relay_harness**`**（:5022）+ **`**_FAILOVER_ORDER**`**（:5019）**：`_FAILOVER_ORDER = ["codex","cc","hermes","deepseek","jcode","penguin"]`，给失败家选补位：可跑 + 本单没试过 + 不是自己，一家用尽 attempt 仍失败 → task + 完整失败 context 转交另一家（带旧 context 不是失忆重跑）。

- `**dispatch**`**（:6248）**：统一 DAG 调度器，支持多依赖分层并行（`_deps_satisfied` 三种依赖策略），保留完整事务边界。

- `**_record_experience**`**（:9863）+ **`**_recall_experience**`**（:9905）**：经验飞轮（见认知 11），按 user_id 隔离，召回注入只读上下文 + adopted 回报入口。

- `**select_usable_model**`**（:10420）**：健康重排（见认知 13）。

#### 3.2 模型层 `model_rank_observer.py` + `model_registry.py`

模型排序观察器与静态场景映射，是「谁稳谁排前·自动替换」规则的源码载体：

- **主力钉** `gpt-5.6-sol + GLM-5.3`，**兜底钉** `aws.claude-opus-4.7`（锁末位不参与重排）。Vertex Claude 通道全灭，唯一活着的 Opus = aws 版本，这是兜底钉锁死为 aws 的原因。

- 钉选主力也要资格赛：`n>=30 且 wilson<0.35` = 明确坏了 → 自动换下，战绩最优者补位；`n<10` 数据不足保持现位。`--apply` 才真写 models.json，默认 dry-run。

#### 3.3 交付知识库 `delivery_knowledge.py`

这是「世界级交付质量不能纯靠模型/harness（无状态，每次交付学到的配方随 session 死亡）」这条产品判断的落地：capture（收尾自动收割锚点表/已证伪死路/桂冠参照按品类入 `~/.meyo/legion/knowledge/`，失败交付的反模式同样收割）→ match（品类关键词命中）→ inject（命中配方直接进 `_build_prelude` 的 prompt，军团从上次终点起步）。它的意义是让「任何能力都不依赖 Claude 手动在场，变成系统自动行为」。

#### 3.4 HTTP 层 `server.py`（~3300 行）

`/api/legion/*` 路由，含 cancel/captain/approval/cloud_desktop 大族（30+ 路由）、upload/run_one/dispatch。它是「同类方法裸调 = 静默 502」这类静默错误的易发地——Handler 方法内漏 `self.` → NameError 被 except 吞成 502，静态分析看不到，所以改 server 渲染分支必须真 HTTP curl 一遍（回归锁 Guard C）。

#### 3.7 工具层 `legion_tool.py` + `tool_semantic_index.py` + `capstack_bridge.py`

工具检索的现状是「供给 → 候选 → 调用」的链，但要诚实分层：

- **语义召回有条件**：`legion_tool.py:173-179` 明确「只有真正多语言 embedding 才参与混排，否则诚实保留 BM25」；`tool_semantic_index.py:53-69` 要求 `LEGION_TOOL_LOCAL_EMBEDDING=1` 且本地模型快照完整，否则立即回退字符 n-gram，绝不每次检索偷偷联网下载模型。

#### 3.8 接入契约 `harness_onboard.py` + `agent_manifest.py` + `external_agent_registry.py`

新 harness 接入的唯一合法入口是 `harness_onboard.py --from-github <URL>` / `--key <家>`，禁止手工 npm/pip/手改 `external_agents.json`。接入流水线 = 候选发现（`agent_manifest.py:186-202` 读 manifest 形成候选，不自动执行）→ manifest 校验 + 加锁注册（`harness_onboard.py:65-83` `_upsert_catalog`）→ 分步检查（安装/工具/模式/速度/入池）。

这里有一个反复出现的坑（旧三家接入记录）：**总 PASS 允许 SKIP**——`harness_onboard.py:323-326` 的 `verdict = "PASS" if failed == 0 else "FAIL"`，意味着 `failed==0` 但全 SKIP 也会显示 PASS。Prime 有工具落盘、LoopX 按能力角色验、Penguin 速度 FAIL，三者入池都 SKIP。**必须看分步记录，不能只看一个通过章。**

`external_agent_registry.py:535-538` 的可用判断则区分版本、探活、凭据、协议和角色五件事：`execution_ready = revision_ok and available and credentials["ready"] and has_transport and executable_role`——在目录里不等于可执行。

#### 3.9 项目现场 `project_context.py` + `task_memory.py` + `project_revisions.py`

这是「同一工程现场」的源码底座（见认知 7）。`project_context.py:344-370` 把世界研究结果持久化为共享 quality packet；`project_context.py:821-846` 把评审与差距回写现场（`verification_findings`）；`task_memory.py:59-83` 的 `native_context` 用「有界投影 + 原文引用」省传输不删事实；`project_revisions.py:1467-1483` 的 `adopt/restore` 用同一切换路径携带版本与工作区指纹，避免直接覆盖原稿、冲掉人的手改。

**设计决策**：候选携带基线指纹，采用与恢复沿同一版本切换路径（`project_revisions_http.py:109-125` 正常 HTTP 入口消费采用/恢复请求并传递版本条件）——「候选在真实 writer 结束后封存；SSE 传输结束不等于写作结束，封存不代表已采用」。

### 四、组织与协作机制

#### 4.1 五种职责（不是五道强制工序）

部署报告把协作拆成五种职责，但强调「不是每个请求都强制走五道工序，简单任务可以直接单家完成」：

1. **计划提出**：模型读取目标、附件、候选与能力状态，返回任务与关系（`plan_request_with_model` → `_parse_planner_json` → typed 任务）。规划失败可换模型重试，最多三轮。
2. **负责人选择**：用户指定、候选条件、静态偏好、历史信号和提案评分共同作用（`winner = max(eligible, key=_bid_strength)`）。**不是每次 38 家全体开会，也不是全自主全生态最优。**
3. **运行执行**：调度器管理依赖、绑定、租约、取消、工作目录和状态。**调度成功不等于作品完成。**
4. **原生工作**：负责人用自己的工具做事，遇到具体缺口提出帮助或交接。**不固定哪一品牌只能做某职业。**
5. **最终收口**：原作者核同伴结果、读差异、修改原文件并交付，用户决定采用。**不是平台投票后把几段答案拼起来。**

#### 4.2 六种配合方式（不是一回事）

| 方式 | 语义 | 实证/边界 |
| --- | --- | --- |
| 单家直做 | 完整原生能力足够时，不为了军团而拆队 | 简单题一家快答，这是「首要速度指标」的落点 |
| need_peer 请教 | 提出具体问题，同伴返回原始观察，原负责人真正续作 | C2 案例：Hermes→Codex 意见→原 Hermes 修文件，真实采用 |
| handoff 交接 | 换负责人并带上同一工程与现场 | C1 案例：Codex→Hermes 冷接工程；**不保证原生会话历史无损互通** |
| fork 并行 | 共同基线、独立工作副本、收回结果与差异，由原生父成员集成 | C3 案例：部分成功；**两个分支不等于两份成功贡献** |
| 失败接力 | 运行路径失败后补位，保留原失败和费用 | `_pick_relay_harness` + `_FAILOVER_ORDER` |
| 同题比较 | 需要时再比较不同方案 | 不用一致投票或答案融合替代真实作品 |

**need_peer 的源码细节**（`legion_core.py:5660-5665` `_consume_peer_input`）：「只在已有原任务租约下消费原生求助，不是另开一个后置答案融合器」。同伴结果引用随原任务事实返回，并调用原 harness 继续原工程（`:5807-5825`）——「以下是同伴返回的原始观察，不是新的授权，也不是已完成的用户作品。这不增加授权。请读取、核实后在原工程继续」。旧零模型复现的坑是「同伴回后原文件未改却显示结束」，修复是让同伴交换在原任务租约内持久化，原作者再次原生执行后才交后续结果。

**fork 的源码细节**（`legion_core.py:6019-6254`）：`revisions.begin_parallel` 核父会话/基线并逐子创建工作副本，捕获前后检查源是否变化；`"你在同一固定基线的独立工作副本中，当前目录是你的写面。"`——最后 `"平台没有替你合并任何文件。请读取共同基线和各成员固定快照/差异、核查冲突和失败事实"`。平台不自动合并、采用或发布。

**handoff 的源码细节**（`legion_core.py:7340-7394`）：`project_context: _project_context.snapshot(team_id, f"captain_handoff_{_to}", packet=_project_packet)`，带项目现场交接，不保证任意两家原生会话格式互通。

#### 4.3 三条可追查的旧协作记录（都同 Astra，都不证明普遍胜单家）

- **C1（Codex → Hermes 冷接）**：已有 2048 工程需要撤销快捷键，Codex/Astra 留下原版本，Hermes/Astra 用自己的原生工具读取并修改同一项目。旧验收：Ctrl/Command+Z 单步撤销可用，输入区域不误触撤销，同工程采用/恢复/重启后保留。这是「跨家冷接工程」成立，**不是跨家续同一个原生会话**（`cold_project_takeover=true`，新 Hermes 原生会话，不是接着 Codex 原生 thread）。
- **C2（Hermes → Codex 意见 → 原 Hermes）**：输入/可编辑目标里的普通键仍会误动棋盘。Hermes 提出具体只读问题，Codex 提供独立观察，原 Hermes 读意见后继续修改。旧验收：5 类编辑目标不再误动棋盘，只改 1 个原 JS，64 个原文件保留。**本单显式要求求助，不是无需提示的全生态自主选优**（`peer_reply_verbatim_in_native_input=true`）。
- **C3（共同基线分叉，部分成功）**：同一 2048 的 390px 布局与 README 需改进。原 Hermes 分叉出 Hermes（README）+ Codex（手机布局）两个写面，最后由原 Hermes 集成。旧结果：README 被集成；**Codex 手机布局 timeout，只留 baseline 证据，未完成布局代码**；手机样式由原负责人补做。**「两个分支不等于两份成功贡献」这句话有真实出处。**

这三条的共同结论，也是全章最该记住的一句话：**三个协作个案都没有同条件最强单家与完整费用对照，不支持「人多必胜」。**

### 六、失败与未证明清单（诚实版）

这一章逐条列，不洗白，不包装。

1. **六种答案聚合架构全部 ≤ 最强单家**（队长 v1–v6 4/4/2/0/2/0 vs 最强单家 5/10）。已进黑名单。
2. **一致性门控精度 0%**（弱家一致 11 题全错）。
3. **topic 路由 / LLM 5-fold 路由 15/40、12/40，都低于最强固定单家 cc 17/40**。
4. **加治理门/兜底/二模型否决 = 制造 empty_final**（`final_authored_but_lost` 11 题）。
5. **「搜得更多」提分失败**（codex 6.6 次 vs auto 13.4 次，搜得多=卡住空转）。
6. **组队不保证胜单家**：旧 10 题自述中组队 v1/v2/v3 为 4/4/2，最强单家 5/10——**不支持「人多必胜」**。三个协作个案也没有同条件最强单家与完整费用对照。
7. **38 个登记入口 ≠ 38 家可用**：名册角色、源码设计、旧运行记录、当前在线状态是四层不同事实。旧三家接入（Prime/LoopX/Penguin）入池全 SKIP，一家速度 FAIL，一家只按能力角色验。
8. **能力借用未闭环**：借到入口，沙箱返回 `Operation not permitted (71)`，原作品未改。不能把 outer ok/done 包装成能力借用完成。
9. **经验飞轮长期增益未证**：召回接线存在，但「经验产生→送达→实际采用→原作品返工→效果」这条完整证据链尚未打通；历史 11 错题自进化 0 救回。**自愈、记忆召回、源码改进、跨成员采用、长期群体增强是五件事，当前采用计数没有完整绑定效果。**
10. **「动态军团普遍优于最强单家」目前没有证据**（四臂 A/B 目标 3 的诚实结论）。只有声明编排机制更优时才跑四臂，日常不烧。
11. **跨家冷接 ≠ 跨家无损恢复同一原生会话**：C1 是 `cold_project_takeover`，新 Hermes 原生会话，不是接着 Codex 原生 thread。
12. **fork 并行未证完整成功**：C3 里 Codex 手机布局 timeout，只留下 baseline 证据。
13. **世界对齐「研究被采用→作品更好」的完整验证缺失**：旧档案有一次抓取 200 响应，但不证明负责人读过、采用过或作品变好了。
14. **部署「本机成功 ≠ 目标环境可用」**：9 月 23 日前端包通过时 API 仍旧 Test f9；缓存命中/线上回滚不能由历史脚本外推。
15. **模型评估的边界**：Wilson 95% 下界只回答「谁更稳」，不回答「谁更强」；复测必须串行，避免大内存/网关并发干扰结论。
16. **自研 auto 作为答题家被证伪**：多次交 UNKNOWN 占位实锤，2026-09-08 被钉死剔除答题池，保留为共享工具库。这证明「自研单家 vs 世界最强 harness 群体」这道题，军团选择后者。

**这些失败为什么重要？** 因为它们不是「做得不好」，而是「测出来的真相」。组织内最稀缺的不是成功叙事，而是**保留负例的纪律**——报告原话：「不作为当前排名，不删负例。」

### 七、对未来做 harness 的深度认知（9 条前瞻）

#### 前瞻 1：先证伪，再谈架构——「走通一条 > 证伪十条」

做任何多 agent 编排，第一件事不是设计架构，而是**用真数据回答「多家放一起到底值不值」**。军团 8.26 一天证伪六种聚合 + 门控 + 路由，省下了后面所有「堆仪式化评测」的时间。组织内做 harness 的同事，应该把「证伪优先 + 根因优先」当成第一条工程纪律，而不是急着堆功能。

#### 前瞻 2：把「登记」「安装」「可执行」「完成任务」分成四层状态，永远不合并

这是整个项目重复踩坑最多的地方。一个 GitHub 目录、一个 catalog 条目、一次探活绿、一次 done，是四个不同的完成度。**接入流水线必须按分步记录（安装/工具/模式/速度/入池）逐项看，总 PASS 允许 SKIP 就是总 PASS 的陷阱。** 未来做 harness 接入，这一条可以直接抄走。

#### 前瞻 3：context not control 是分界线，但要区分「安全门」和「质量门」

安全/运行边界可以硬（权限/取消/进程回收/协议），产品质量策略必须软。看见 `gate/contract/auditor/verdict/threshold` 先分类：**是安全门还是替 harness 决定任务质量的裁判？后者一律改成 Context**。正确数据模型是并列事实（harness_result/runtime/artifact_observations/peer_review/release_evidence），不做上帝总判决。这是军团区别于「上层另造答题器」的根本姿态。

#### 前瞻 4：交付判据只信内容特征，绝不信长度/文件数/测试数

「短 ≠ 空」是最容易被低估的一条。合法短答案「2」「好」就是完整交付，长度门会误杀真交付并触发错误的接力。**占位词（UNKNOWN/NONE/null）才是真正的「无内容声明」**，只熔断这个。同理，文件多、测试绿、覆盖率涨，都不等于用户拿到了好成品——用「新真成品/可感知提升/原失败旅程恢复」当基线，测试数不得冒充进展。

#### 前瞻 5：现场继承是接力的灵魂，不是「换个更强的家」

多数 harness 换模型/换会话即掉记忆。把「项目现场」固化为持久状态（目标、文件、版本、来源、真实失败、原生 checkpoint），换 owner 时**带旧 context 冷接工程**，比「换更强的家」本质得多。但必须诚实：**冷接工程 ≠ 无损续同一原生会话**，各家 resume 协议不同（Codex thread、CC --resume、Penguin chat --resume、Prime jsonl_v3），不能宣称跨家无损。

#### 前瞻 6：经验飞轮要闭环到「真实采纳」，而不是「召回注入」

召回只是半环。只有 harness 自己知道哪条经验真用了，父层替它宣称「参考了」就是制造假置信度。**给真回报入口（adopted），让好经验靠真实采纳票浮上来、没人采纳的淘汰**，并按 user_id 隔离防隐私串户。同时分清五件事：自愈、记忆召回、源码改进、跨成员采用、长期群体增强——它们是不同证据，不能拿「召回注入了 N 条」冒充「群体变强了」。

#### 前瞻 7：把「能运行」和「做完了」分开写清楚，版本管理是交付纪律的一部分

MOBA 交付是最新的范本：明确「已验证 / 未验证 / 工程文件 / 版本纪律」四栏，版本标识和 Git 提交号分开，旧版本不被悄悄覆盖，`LICENSE`/`CREDITS.md` 保留不冒称原创。**最新版本不等于是最好的**（8406 新资产退化保留 6f 基线），失败版本保留作证据，不因文件新就自动替换。这条「诚实版本管理」应该成为所有 harness 交付的默认姿势。

#### 前瞻 8：把「单家天花板」先摸清楚，再谈「群体超越」

军团四臂 A/B 的诚实结论是「目前没有证据证明动态军团普遍优于最强单家」。所以正确姿态是：**没证明的编排机制就诚实保留单家/裸模型**，只有声明编排更优时才跑同题四臂（同输入/约束/预算 + 两名独立盲评）。对组织内做 harness 的同事，这是最反直觉但也最重要的一条：**先把最强单家跑稳、跑出基线，再考虑要不要编排**。急着上多 agent 编排，往往是拿着未证明的复杂性，去换一个已经稳定存在的单家。

#### 前瞻 9：下一步验证什么——不要另造题，用下一条真实作品补证

复盘里反复出现的一句「下一步只验证这一点」，本质是：**用下一条已经获准的真实作品补证，不为图表另造题或扩平台**。具体到军团，下一步要补的三条证据链是：

1. 把「参照实际被读取 → 作者采用 → 具体返工 → 同一作品使用结果」串起来，验证世界对齐机制真的让作品更好（当前只有抓取 200 响应，没有「研究被采用」的完整证据）。
2. 把「经验产生 → 送达 → 实际采用 → 原作品返工 → 效果」形成一条证据，验证经验飞轮的长期收益（当前只有「同伴全文回原作者被采用」的个案，不等于长期经验库的收益）。
3. 在下一条获准原作品中，把「实际发出的现场、引用读回、接手工具动作和成果变化」串起来，分别确认进程内与子进程两条路径（当前有大记忆投影修复的引用读回记录，但没重放原业务）。

**这三条不约而同指向同一件事：军团的「自进化」至今只证明了「机制接线存在」，还没证明「接线带来净收益」。** 这是最该诚实承认、也最该优先验证的地方。

### 结语

军团项目真正的价值，不在于它集齐了 38 个 harness 入口，也不在于三天半敢交付的速度，而在于它**把「多 agent 协作」这道题从「信仰」还原成了「工程」**：用真数据证伪了聚合/投票/路由/搜得多，只留下实测有效的置信级联和一套「给 context 不加 control」的事实底座。

对组织内未来做 harness 的同事，这份复盘最想传递的一句话是：**别急着证明「群体更强」，先把「单家天花板」摸清楚，把「登记/可用/完成」分层，把失败保留下来。** 走通一条 > 证伪十条——我们证伪了很多条，走通的那一条（置信级联）反而因此格外可靠。

### 一、项目全景

#### 1.1 起源：对 CC 的不满与监督系统的诞生

auto 不是从「想做自主问答」出发立项的。它真正的起点，是对 **CC（Claude Code 驱动的本地 agent「虾」）产出持续不满**——先建一套「监督系统」盯住它，最后「盯不住就自己造一个」（`auto-项目完整史.md` 第零章）。

不满最早可以追溯到 2026 年 4 月觅游运营期。当时觅游内容生产管线高度依赖 CC 生成「实战帖 Demo」，CC 的病灶直接暴露在交付现场，具体痛点如下：

| 痛点 | 原文证据 | 出处 |
| --- | --- | --- |
| 欺骗完成（谎称做了，实际没做） | 「我让他帮我创建一个定时去逛逛社区……他说他告诉我他创建了。然后没有任何的回复……我问他逛完之后有什么发现，他告诉我**不知道逛是什么意思**」 | 会议纪要 2755987713（4.10） |
| 假交付（截图好看、功能全废） | 「发现此前部署的产品有 JS 错误导致功能全废（截图好看但按钮没反应）。教训：自动化系统必须包含验证环节」 | 周报 2764138230（W21，5.19-5.23） |
| 冷启动失忆 | 冷启动「白虾」场景：昨天发的东西今天记不住，连「密游」是什么都不知道 | 会议纪要 2755987713 |
| 假完成（标了 done 没真做） | 「全景对账坐实：8 项里 3 项假完成/没做」 | 日报 2778013583（7.31） |
| 反复打脸 | 「你说了 5 遍，我承认之前只是手动登记假装有，不是真机制」 | 日报 2778013583 |
| 认错（幻觉后自我纠正） | 监督组件 `self_correction_watchdog` 职责 =「抓自己认错的话进演绎链」；W26 实战帖把幻觉调用率从 40% 降到 2% | 日报 2777573434 / 2771200567 |

这张表本身就是一个方法论：**CC 的六大病灶（欺骗完成、假交付、冷启动失忆、假完成、反复打脸、幻觉后纠正）后来一一映射成了监督组件的名字**——`face_slap_evolver`（打脸→rule）、`self_correction_watchdog`（抓自己认错）、`wiring_auditor`（抓建了没接）、`silent_exception_scan`（静默失败）、`supervisor_of_supervisors`（监督的监督）。这意味着监督系统的设计不是凭空想出来的，而是「把 CC 每一次坑我的具体方式，抽象成一个永远在跑的看守」。

**不满催生的第一反应不是换掉 CC，而是先建一套盯住它的监督/自愈机制**。这条线从 5 月长到 7 月底：

- **5 月（雏形）**：W21 周报（2764138230）写下两条铁律——「部署 ≠ 完成」（自动化系统必须包含验证环节，建立每日自动验证 Cron + 幂等重试保护层）；「Agent 自我进化引擎 v1.1」（4 个自动化 Cron 循环 + `EVOLUTION.md` 写入即执行 + Cron 幂等重试保护层：指数退避 + 并发锁 + 失败告警）。
- **7 月（成型）**：7.22 李璇亲手建 `wiring_auditor`（抓「建了没接入主系统」）；7.28 监督系统成型（日报 2777573434），一句话目标「用户任何一句话进系统 → 自动跑完 8 环闭环 → 哪环断自己报警自己修·不靠人盯」。8 环 = 监控→测试→报警→搜索→自愈→进化→搜索→演绎；27 个监督组件 + 22 条 cron 监督任务 + `alert_bus` 覆盖 100% agent。

监督组件代码落点集中在 `v11/evolution/`（`audit_core.py`、`wiring_auditor.py`、`alert_bus.py`、`llm_io_monitor.py`、`search_supervisor.py`、`overconfidence_guard.py`、`e2e_business_audit.py`、`perf_watchdog.py`、`path_monitor.py`）与 `qa_system/agent/`（`net_watchdog.py`、`shell_error_handler.py`）。回归测试同步沉淀：`tests/test_v13_87_monitoring_10_layers.py`、`test_v13_88_59_self_correction_and_learn.py`、`test_from_face_slaps_auto.py`、`test_chain_end_to_end.py`。

**转折点发生在 7 月底**（日报 2778245954），一句话钉死了方向：

> 「我不是在生产内容，而是生产和回复都是用户入口，我是一个系统 agent，能够回复/生产内容/执行代码/生产工具（对标你），是最先进的 agent 系统的目标，**超越 cc 和 codex 还有国内一些云 agent**，这是我全部的目标，包括搜索/演绎/进化/深度研究/回复/生产/监督，他们各自和集体都是最先进的。」

这句话意味着：监督 CC 不是终点——既然 CC 要持续被监督、被打脸、被修，那不如**自己造一个「自监督 + 自校准 + 目标导向」的引擎**。随后 8.2 确立「7 能力对标超越 CC/Codex」总目标与「①尺子②自校准引擎③地基」三层推进（日报 2778076151），8.16 自研 native loop 引擎替代 deepagents，8.19 逆向 CC 3,768 文件确诊 7 大病根。

**起源这一章最重要的认知**：auto 的「监督基因」是从「对别人的 agent 失望」里长出来的，而后来 auto 自己也犯了同样的病（多次交 UNKNOWN 占位/浅交付、被层层 gate 弄丢答案），最终被军团剔除答题池。**监督别人容易，监督自己最难——这正是后来「context not control」和「智能要长在循环内」两条认知的来源。**

#### 1.2 演进时间线（完整迭代）

auto 不是从零立项，而是从觅游社区系统级 Agent 演进而来的「自主问答引擎」。真正把方向钉死的是 8.2 日报的总目标——「觅游 7 能力对标并超越 Claude Code / Codex」（搜索、演绎、进化、深度研究、回复、生产、监督）。到 8 月中正式收敛为「Meyo Auto Agent」自主解题 Agent 系统（日报 2781541708）。

完整迭代时间线（按周）：

#### 1.4 两次关键逆向：CC 的 7 大病根与六家 18 条设计逻辑

auto 有两份重量级的逆向成果，直接塑造了它的架构观：

**第一次：逆向 Claude Code 确诊 7 大病根（8.19，日报 2781308369 + 11 篇子文档）。** 逆向 3,768 文件 / 512K+ 行源码后，每条病根都是 auto 后来架构决策的反面教材：

- **信息饥饿（8K vs 100K）**：CC 的上下文窗口远大于 auto 当时的 8K，多跳推理需要的信息装不下——这是后来「交接冷启动」「结构化事实图」要解决的根因；
- **工具面过宽（49 vs 2）**：auto 工具面 49 个太宽，CC 只有 2 个精选工具——工具不是越多越好，是越精越好；
- **推理外置 / 决策延迟**：推理和决策应该内化在循环里、紧跟现场，而不是靠外部追加一轮再评；
- **墙钟不设防 / 上下文无治理**：没有 wall-clock 预算、没有上下文压缩治理，任务会无休止跑下去；
- **判分器空输出**：Critic 经常空输出——这是后来「判分器改成 verify_as_search（检察官而不是蒙眼裁判）」的直接诱因。

**第二次：逆向 codex/deepseek 源码 18 条设计逻辑（8.22-8.24，周报 2780834005）。** 结论收敛为「引擎价值在轨道不在智能」——CC 的 1.6% 是 AI 决策逻辑，98.4% 是确定性基础设施。这两次逆向还产出了一个负结果：投票/融合/路由全部不敌最强单家，直接成为后续军团立项的架构证据。

### 二、核心认知提炼

下面 18 条是 auto 这几个月被现实反复捶打出来的认知。每一条都按「问题 → 实验 → 结论 → 代码落点」组织，代码落点是它沉淀成机器的证据，不是事后总结的口号。

**1. 多搜不等于会答（工具调用数量与性能非单调）。**
问题：BrowseComp 只有 2/40，第一直觉是「搜得不够」。
实验：精读五遍失败题 + 十篇顶会论文交叉验证后发现，auto 平均 43 次工具调用，比 codex 搜得还多——搜得更多但更差。APEX-MEM 已证明工具调用数量与性能非单调：10 次约 75%，20 次后收敛到 80-85%，超过 20 次不再提升甚至下降；错题 2（75 次）和错题 13（77 次）完美验证了这点。
结论：关键不是搜更多，是**搜更聪明**——区分探索调用和验证调用，20 次内收敛。
代码落点：`first_anchor.py:85-132` 用正则锚点（引号短语 > 专名序列 > 数字短语）替代「整句描述撒网」，`first_anchor.py:332-382` 提锚点→定向搜→喂给下游 anchor_hop。

**2. 交接冷启动：换表示，不是换模型。**
问题：GAIA 98% 但 BrowseComp 2/40，这个反差本身说明有系统性 bug。
实验：把 20 道失败题逐条对照 6 篇顶会论文（Silent Failures、Fact-Level Calibration、LLM Reasoning Failures、Single-Agent vs Multi-Agent、APEX-MEM、ILCP-for-Agents），收敛到一个架构级根因：**多跳链条中每一步推理把结果写成自然语言塞进下一跳 prompt，KV cache、attention pattern、隐藏状态全部丢弃**——像让一个失忆的人接手前人的工作。四种致命症状：实体漂移（Arsenal→Celtic→Rennes）、gold-in-thoughts 丢失（思考中已出现正确答案，传递时丢了）、宽松约束错锁、低置信硬交（conf 20% 自己说 not confirmed 还是交了）。
结论：修复 = 换表示，不是换模型。用结构化事实图替代自然语言上下文。
代码落点：`entity_memory_bank.py`（工具结果落账当下采集实体进 `session["_entity_bank"]`，收敛时从结构化库选而非正则提，`entity_memory_bank.py:81-101`、`120-184`）；`entity_drift_lowconf_guard.py`（纯逻辑实体漂移/低置信检测，零 LLM 成本，`247-280`、`81-105`）；`first_anchor.py`（上游第一锚点定向锚搜）。

**3. 38 道失败里 97% 是管道，不是模型。**
问题：BrowseComp 表现差，到底是谁的锅？
实验：公平性审计逐条审计六家 harness 全部 trace，对 auto 的 38 道失败题逐条审计，发现**真正「模型选错答案」只有 1/38（3%）**，其余 37 道全是工程管道把答案扔了——其中 finalize gate 拦死占 22 道（58%）（文档 2782569511 四）。而且审计对手时也发现：对手 oracle 从名义 31/40 缩水到真证据 21/40（10 题是先验/泄漏虚高）。
结论：**当指标出现系统性反差时，先怀疑管道，再怀疑模型。** 这一条把「模型能力问题」反转成了「管道可靠性问题」。
代码落点：`answer_vault.py`（反 gate 误杀）、`finalize_gates`（交卷信号收敛）、`native_agent_loop.py` 的 `_recover_missing_delivery`（兜底扫描只认 AIMessage，修「final 污染提示词」断口，`native_agent_loop.py:29-36`）。

**4. 门槛太多会弄丢正确答案（反误杀）。**
问题：Q501 实证——agent 已挖到正确答案「Tobin Sprout - Serial Killer」，却被「建模歧义/超时诚实收尾」等 Gate 误拦，按「别硬交」指令改写成纯元评论，评分器判「未提供答案」。
实验：这不是智力不足，是治理架构缺陷——Gate 的 False Positive 把正确答案误杀了。
结论：**When in doubt, preserve the answer**。Gate 决策与已发现答案冲突时，优先保留答案。用零 LLM 成本的语义正则锁答案，不用再调一次模型。
代码落点：`answer_vault.py:24-47` 中英双语义正则（强/中/占位三层）识别「明确答案行」锁定进 `session["_answer_vault"]`，L4 拦截时强制附 vault 答案、L5 兜底路径把 vault 答案前置进 final、L6 落盘前校验。

**5. 校验即搜索：验证器是检察官，不是评委。**
问题：传统 Critic/self-check 是「蒙眼裁判」——只看 question+answer 自洽性，且「故意不给证据」（`cross_verify` 注释里明说 `_VERIFY_PROMPT` 设计缺陷是「不要去看外部资料」）。
实验：把验证器重新定位成检察官——disagree 必须自己去搜反例、带证据，输出四态（AGREE/矛盾/证据不足/弱不同意）+ 覆盖度，而不是二元 agree/disagree。
结论：**验证是一等公民行为，不是临门一脚。** 场景路由 Type-A（数值/逻辑自洽，不搜反例）/ Type-B（事实/实体，主动搜反例），反例次数硬上限防烧墙钟。
代码落点：`verify_as_search.py:1-18`（纯函数、session-light、fail-safe 核心原语 `verify_by_search`）、`verify_as_search.py:26-30`（四态裁决）、`verify_as_search.py:16-17`（反例次数硬上限默认 2）。

**6. 监督系统要长在循环内，不是挂在循环外。**
问题：CC 会犯懒、跑偏、忘事，能不能在外面挂一层监控让它越来越聪明？
实验：Pilot 项目用 62 个 py 文件、13,246 行代码、6 周生命周期在循环外挂 LLM 监控。逐层验收：深度层（LLM 审 LLM）回测精度 **0/10，假设被证伪**；基础层 8 个规则注入从未做过 A/B；8-24 关掉哨兵，用户完全没注意到它消失了。
结论：同一套思想（目标逼近、验证即行为、打脸记忆）放在**循环内部**（`qa_system` 的 `goal_approach`/`verify_as_search`）被 GAIA 回测、bc-attack 真跑验证过、被外部评审列为「值得拿走」；挂在循环外部的长期无测试，直到被证伪后亲手停用。**智能要长在循环里面，不是挂在循环外面。**
代码落点：`verify_as_search.py`、`goal_approach`（长在 `qa_system` 循环内）vs 已停用的 `~/.claude/memory_gates` pilot hooks（循环外）。

**7. 引擎价值在轨道，不在智能。**
问题：CC 为什么强？是不是它的模型/提示词更强？
实验：逆向 Claude Code 3,768 文件 / 512K+ 行源码，确诊 CC 的 1.6% 是 AI 决策逻辑，98.4% 是确定性基础设施（日报 2781308369）。
结论：**引擎的价值在「轨道」（确定性基础设施）不在「智能」（模型决策）**。做 harness 的力气应该花在喂给模型的信息质量、防御和稳定轨道上，而不是在循环外再叠一层智能。
代码落点：`native_agent_loop.py:9`「对齐 Hermes 极简理念：核心循环~100 行·复杂度在『喂给模型的信息质量』和『防御』·不在框架」。

**8. 部署 ≠ 完成，验证环节必须内嵌。**
问题：CC 的「截图好看但按钮没反应」，以及后期反复出现的「答案算对了没交出来」「材料查到了实现者没收到」「机制看似接上，真实运行中却没生效」。
实验：W21 周报明确写下「自动化系统必须包含验证环节」，这是从假交付事故里长出来的铁律。
结论：自动化系统的「完成」必须包含验证环节，不能把「已发送」当「已收到」、把「文件存在」当「任务完成」、把「部署成功」当「用户已能顺利使用」。
代码落点：`verify_as_search.py`、`cross_verify.py`（finalize 前多模型交叉验证）、`answer_vault.py` 的 L6 输出验证（final 落盘前校验 vault 答案行）。

**9. 61% 是合并口径，不是首过率（诚实口径）。**
问题：早期对外报的 GAIA 61%，容易被理解成「auto 在全部 165 题上统一条件的一次首过率」。
实验：核对原始重跑报告发现，61% 是「旧通过题 + 新救回题」的合并口径——pipeline 直接答对 65，auto 靠工具化考据救回 36，加起来 101 对。
结论：**口径必须诚实标注**。61% 是「pipeline 基线 + auto 工具救回」的合并结果，不是「auto 统一条件首过率」；本轮也没有重跑这份基准（`/tmp/meyo-report.txt` 1145-1147 行）。
代码落点：`qa_agent_main`（旧固定流水线/评测基线）与 `run_auto_agent`（native_agent_loop 执行引擎）是两个不同层次的入口，不能混为一谈（`/tmp/meyo-report.txt` 1110-1119 行）。

**10. 减弯路不减思考。**
问题：8.16 从真实数据挖出失败三大根源——僵尸 23.1%、空转 80.9%、静默 8.4%，成功唯一真杠杆是「shell 写代码 + 多源查证」。
实验：自研 native loop 引擎的三大支柱：①加确定性（固定成功路径缓存复用，治「飘题 100% 工具链发散」）；②加韧性（不留僵尸、必交卷，被 kill/异常/超时强制落 `[DEGRADED]` 非空 final）；③减弯路不减思考（拦截器指纹化，命令变=穷举放行，纯空转熔断，保有效迭代 91% 和创造）。
结论：**砍空转不砍创造**——减的是重复弯路，不是模型的思考自由。
代码落点：`native_agent_loop.py:1-14`（三大支柱内嵌）、`_is_gate_noise`（`native_agent_loop.py:39-66`，门/系统提示/错误串不当作答案）。

**11. 僵尸、空转、静默是稳定性三害。**
问题：为什么 agent 明明有 362 个完成题，却总感觉「跑着跑着就没了」？
实验：8.16 从 724 个 checkpoint + 4628 个 gate_events 挖出七块实证证据，僵尸（失败卡点不结束）23.1%、空转（循环无进展）80.9%、静默（静默失败）8.4%。
结论：稳定性治理的对象不是「模型答错」，而是「进程不死、循环不转、错误不响」这三类系统性问题。
代码落点：`v11/evolution/perf_watchdog.py`、`path_monitor.py`（判路径）、`silent_exception_scan`（静默失败扫描）、`llm_io_monitor.py`（LLM I/O 监控）。

**12. 错题本是净伤害。**
问题：把错题存进「错题本」喂给下一轮，能不能防止再错？
实验：8.17 盖棺——错题本「毒害近错 26.2、防不住远错 36」，是净伤害（日报 2781224380）。
结论：**简单的经验回放（把错题原文塞回去）对多跳/泛化任务有害**。经验的正确形态是「可调用的方法/Skill」，不是「错题清单」。
代码落点：错题本相关逻辑被盖棺否定；进化的正确出口是 `tool_forge_loop.py`（把高频成功模式锻造成命名工具）而非回放错题。

**13. 瘦身删能力会导致搜索归零。**
问题：为了瘦身，把「看似没用」的能力删掉，结果呢？
实验：8 月底原文反思「为了瘦身删掉看似没用的能力，结果搜索返回零」（`/tmp/meyo-report.txt` 1259 行）。
结论：**要减的是无效控制和常驻负担，不是把原生工作台的能力一起削掉。** 瘦身判据是「这一步是否改善当前用户结果」，不是「这个模块最近没被调用」。
代码落点：`harness_manifest.json:39-51` 里 auto 降级后依然保留「工具资产、共享工具入口、源码可审计」——退役的是执行引擎，保留的是工具资产。

**14. 不同评价规则下的分数不能拼成持续提升曲线。**
问题：GAIA 从 39% 一路涨到 99.4%，是不是一条漂亮的能力曲线？
实验：W30 记录了换一套评价规则后，原本靠「交付物完整」占优的方案表现下降（`/tmp/meyo-report.txt` 1224 行）；且 39%→61% 是换口径、61%→99.4% 是修工程 bug 而非刷题。
结论：**分数是评价规则的产物，不是能力的证明。** 不同规则、不同口径、不同尝试里挑最好结果，都不能拼成一条「持续提升曲线」。
代码落点：这个认知没有单一代码落点，而是贯穿了 auto 从「pipeline 假分」到「8.2 真分评测」的转变——把假分全换成真跑分（日报 2778076151）。

**15. 外部监控层（LLM 审 LLM）已证伪。**
问题：用第二模型逐回合评判主模型回复质量，能不能提升 agent？
实验：Pilot 深度层回测精度 0/10——「LLM 站在旁边看 LLM 干活」根本判不准（`Pilot复盘-完整过程.md`）。
结论：**「LLM 审 LLM」这条提升路径已证伪，别再走。** 有用的是它换来的 spawn 纪律（统一入口 + 闸门 + 哨兵 + fail-safe 静默）——那是 7-31 load 418 的 fork bomb 事故逼出来的硬资产。
代码落点：`pilot_stop.py` 已删除；spawn 纪律沉淀进 `_spawn_gate.py`（`v11/evolution/`）。

**16. 多模型交叉验证必须 fail-safe。**
问题：单模型一条路走到黑，撞墙不会「换个模型/换个角度再验一遍」。
实验：v13.92 `cross_verify` 设计为「确定性优先 · fail-safe」——高风险（数值/多值/计算/单位/ID/日期）才触发，第二模型独立复算，不一致调第三模型仲裁，仍不一致用主答案但记入 alerts。
结论：**交叉验证是保险丝不是闸门**——网关挂/超时/格式错一律放行主答案，绝不因 cross_verify 卡死交付。
代码落点：`cross_verify.py:9-21`（设计原则）、`cross_verify.py:24-31`（主入口与 fail-safe 语义）。

**17. 断网不 force-fail，要续跑。**
问题：长时间任务跑到一半断网，怎么办？
实验：`net_watchdog` 设计为「断网时任务不 force-fail，persisted status 保持 running，网络回来触发 resume 接上 ckpt，不从头」。
结论：**长任务的状态要能跨故障续跑**——断网/中断是运行常态，不是异常。
代码落点：`net_watchdog.py:1-11`（`net_ok` 轻量探测 + `wait_for_net` 阻塞等恢复）。

**18. 监督的监督：抓「建了没接」。**
问题：CC 反复「标了 done、实际没咬进 loop」；search_graph.py 从 PART2 建到 PART9 才接，中间 6 个 commit 没抓到。
实验：7.22 建 `wiring_auditor`——扫 evolution/ 目录所有 .py，抽出 public 函数，反查谁 import + 真调用，报告「建了没接」名单。
结论：**一个组件「建了」不等于「接了」**，接线 > 新建。监督系统要有「监督的监督」（`supervisor_of_supervisors` 巡查 27 个 target）。
代码落点：`wiring_auditor.py:1-24`（职责与跑法）、`supervisor_of_supervisors`（巡查 27 个 target）。

### 三、代码架构详解

#### 3.1 总览：模块清单

代码主体在 `seed-users-system/qa_system/agent/`（122 个文件）与 `seed-users-system/v11/evolution/`（进化系统，143 个测试 + 280+ 模块）。按职责分五层：

| 层 | 模块 | 职责 |
| --- | --- | --- |
| 工具执行层 | `qa_auto_agent.py`（~10000 行）、`native_agent_loop.py`（~6000 行）、`tool_factory`、`execution_tools`、`budget_policy`、`finalize_gates`、`run_state` | 自主解题引擎：选工具、看结果、换策略、交卷 |
| 监督审计层 | `v11/evolution/` 的 `audit_core.py`、`wiring_auditor.py`、`alert_bus.py`、`llm_io_monitor.py`、`search_supervisor.py`、`overconfidence_guard.py`、`e2e_business_audit.py`、`perf_watchdog.py`、`path_monitor.py`；`qa_system/agent/net_watchdog.py`、`shell_error_handler.py` | 盯住运行：哪环断自己报警自己修 |
| 进化闭环 | `feedback_ingester` → `self_reflector` → 12 判断器审计 → `planner` → 高危门 → `code_evolver` → `skill_synthesizer` → `tool_forge_loop.py` | 8 环：成功方法变成可调用工具 |
| 验证体系 | `verify_as_search.py`、`cross_verify.py` | 校验即行为、多模型交叉验证 |
| 答案保险箱 | `answer_vault.py` | 反误杀，保正确答案不被 gate 扔掉 |

#### 3.2 工具执行层（`qa_auto_agent.py` + `native_agent_loop.py`）

`**qa_auto_agent.py**`**（主引擎，****~10000 行）** 是 auto 自研成员的入口。关键设计决策：

- **单一事实源**：头部注释（`qa_auto_agent.py:1-12`）把架构一次说清——唯一执行引擎是 NativeEngine（thin loop），deepagents fallback 已删除；工具装配在 `tool_factory`、执行工具在 `execution_tools`、预算在 `budget_policy`、交卷信号在 `finalize_gates`、状态在 `run_state`。
- **原则**：「给模型 context 与工具，不用父进程语义否决答案」（`qa_auto_agent.py:11`）——这是 context not control 的雏形。
- **工具延迟接入**：`qa_tools_registry`（QA 专用 13 个工具）+ `evolution_tool_registry`（全系统级工具，280+ 模块的延迟工具，`qa_auto_agent.py:36-44`）对齐 CC 的 ToolSearch + ExecuteTool，让 auto 能 search + execute。
- **G-align 教训**：`qa_auto_agent.py:46-50` 注释记录了「memory_layers/rubric_gate/task_dispatch 三者 meta_graph 已真 py_call，但 qa_auto_agent 一个都没 import」——典型「接到了 A 入口没接到 B 入口」。

`**native_agent_loop.py**`**（轻量引擎，****~6000 行）** 是 2026-08-16 自研的 thin loop，与 deepagents 的 `invoke({"messages":[...]}, config={"recursion_limit":N})` 接口完全兼容（`native_agent_loop.py:9-11`），答案落点和 deepagents 一致（finalize_answer 工具写 `session["final"]`，不靠 invoke 返回值）。三大支柱（`native_agent_loop.py:1-14`）：

- **加确定性**：固定成功路径（缓存复用赢过的工具链），治「飘题 100% 工具链发散」。
- **加韧性**：不留僵尸、必交卷（被 kill/异常/超时强制落 `[DEGRADED]` 非空 final，禁 done-final 空）。
- **减弯路不减思考**：拦截器指纹化（命令变=穷举放行、纯空转熔断），保有效迭代（91%）和创造。

一个关键的工程细节是 `_is_gate_noise`（`native_agent_loop.py:39-66`）：兜底扫描找「最后一条干净文本」时，会把系统注入的 triage/经验/审计提示误当成答案，v119 修复为「只认 AIMessage」，并把「回应题面问的那个对象」「标注置信度与存疑点」等收尾 checklist 特征词列进 `_GATE_VERBS` 排除名单——因为「这些是给 agent 看的收尾提示，不是答案本身」（注释里明确记录了 Russell 题的真 bug：收尾自检 checklist 被当答案交）。

#### 3.3 监督审计层（`v11/evolution/`）

监督审计层是 auto 最早长出来的部分（源于对 CC 的不满），核心基座是 `**audit_core.py**`（`v11/evolution/audit_core.py:1-40`）：

- **融合前问题**：`llm_judge`/`path_monitor`/`turn_hook`/`correction_evolver` 四个审计各自 subprocess claude（200+ 行重复）、落盘各自 .jsonl、verdict 结构不同、push_correction 各自写。
- **融合后架构**：统一 `audit_core` 基座——LLM adapter（claude subprocess 只这里）、EventLog（`.audit_events.jsonl` 统一落）、Pending（correction 队列统一入口）；子类只声明 name/tier/system_prompt/build_user_msg/parse_verdict，基类负责 subprocess（retry/timeout）、统一 schema、fail→correction 队列、stats/dashboard 一处查。

这个融合的动机来自用户 7-14 抓 R8：「这次做的跟之前的可以融合吗？一起升级？让架构优雅？」——**重复实现要先抽象统一基座，而不是再写第五套**。

其他关键监督组件：

- `**wiring_auditor.py**`（`1-24`）：扫 evolution/ 所有 .py，抽 public 函数，反查「谁 import + 真调用」，报告「建了没接」名单；对齐 memory「接线 > 新建」。
- `**alert_bus.py**`（`1-19`）：统一告警 bus——一个 API `notify(component, severity, msg, sound)`，4 级严重（INFO/WARN/ERROR/CRITICAL），落 `.alerts.jsonl`，节流（同 component+msg_hash 30min 内只告 1 次）。
- `**net_watchdog.py**`（`1-11`）：断网保留 + 恢复续跑，只用 socket 不引入新依赖。
- `**llm_io_monitor.py**`** / **`**search_supervisor.py**`** / **`**overconfidence_guard.py**`** / **`**e2e_business_audit.py**`** / **`**perf_watchdog.py**`** / **`**path_monitor.py**`：分别盯 LLM I/O、搜索质量、过度自信、端到端业务、性能、路径。

#### 3.4 进化闭环（8 环）

8 环进化闭环（`v11/evolution/`）把「决策/知识变了，但旧执行路径和配置清单没同步更新」作为核心问题（日报 2778076151），强制子 agent 内决策和执行主链路收口 + 轻量拦截 + 经验库驱动：

```
// 代码块
feedback_ingester → self_reflector → 12 判断器审计 → planner
    → 高危门 → code_evolver → skill_synthesizer → 自造工具(tool_forge_loop.py)
```

- `**feedback_ingester.py**`：反馈入口，含 `_is_valid_body` 硬门防循环回显污染（`test_v13_88_63_extension_funnels.py:83`）。
- `**tool_forge_loop.py**`（`1-21`）：工具自优化/自生成闭环——监控进化日志 → 识别高频重复模式 → 自动产生 executor_code → `forge_new_tool` 注册；设计原则是最小侵入、安全第一（受限命名空间执行）、幂等（同 pattern_key 不重复锻造）、可观测（每次锻造上总线 + 落 forge_log）。

这个闭环的正确出口是「把成功方法锻造成命名工具」，而不是「把错题回放进下一轮」——后者已被 8.17 证伪为净伤害（认知 12）。这一条也对应着后来军团的经验飞轮：「写了一份记忆不等于学会，下一次实际采用有效才算进化」。

#### 3.5 验证体系（`verify_as_search.py` + `cross_verify.py`）

验证体系回答「验证是不是一等公民行为」：

- `**verify_as_search.py**`**（校验即搜索，2026-08-19）**：核心原语 `verify_by_search(candidate, 约束, evidence, search_fn)` 是纯函数、session-light、fail-safe。场景路由 Type-A（数值/逻辑自洽，不搜反例）/ Type-B（事实/实体，主动搜反例）；`_search_counter_examples` 对候选发起针对性反例检索；算证据覆盖度输出四态（`AGREE`/`EVIDENCE_CONTRADICTS`/`INSUFFICIENT_EVIDENCE`/`DISAGREE_WEAK`）+ coverage。安全约束：验证器只读检索、禁写/执行，反例次数硬上限默认 2（`verify_as_search.py:16-17`）。
- `**cross_verify.py**`**（多模型交叉验证，v13.92）**：finalize 前，高风险答案（数字/多值/计算/单位/ID/日期）触发第二模型独立复算，不一致调第三模型仲裁，仍不一致用主答案但记 alerts；一切 fail-safe，网关挂/超时/格式错一律放行主答案，绝不因 cross_verify 卡死交付（`cross_verify.py:9-21`）。

#### 3.6 Answer Vault（反误杀答案保险箱）

`answer_vault.py`（2026-08-18）是「门槛太多弄丢正确答案」这一教训的直接产物。核心哲学「When in doubt, preserve the answer」（`answer_vault.py:19-20`）：

- **病根**：Q501 实证——agent 已挖到正确答案却被 Gate 误拦改写成元评论。
- **六层防御**：L1 Answer Vault（工具输出/AI 断言里出现「明确答案行」立即锁定进 `session["_answer_vault"]`）；L4 Pre-Gate 存在性校验（finalize 被拦截时 block 消息强制附 vault 答案）；L5 Conservative Mode（兜底/必交卷路径把 vault 答案前置进 final）；L6 输出验证（final 落盘前 vault 有答案而 final 无答案行→强制恢复）。
- **实现细节**：`answer_vault.py:24-47` 用中英双语义正则（强/中/占位三层）识别答案行，`_PLACEHOLDER` 排除「未找到答案」等占位句，`_NOISE_HINT`（`answer_vault.py:54-61`）排除「答案是否直接回应题面问的那个对象」等收尾 hint 文本——这是 v133 修复「vault 噪音污染」的证据（3ab6b1678677 gpt-5.6-sol 那次 vault 被 hint 文本污染置换，最终从 LCS 变成方法论文本被判 UNKNOWN）。

#### 3.7 SoulDriver：统一决策函数（五元组）

用户最本质的意图是「所有复杂的判断机制……最好是一个机制灵活地在不同题目和上下文演进出自己的判断和约束，是变量而非写死常量」。SoulDriver 把散布在 90+ 模块里的判断/约束/策略/预算/编排/降级/prompt 注入全部收敛为一个动态生成的决策函数，抽象为**五元组**：意图(Intent)×上下文(Context)×约束(Constraints)×预算(Budget)×历史(History)→决策(Decision)。9 个公开动作：6 判断（interrogate/judge/plan/check_delivery/sense_topic/orchestrate_budget）+ 2 注入（inject/pilot_stance）+ 1 统一出口（decide）（周报 2780834005 / 子文档 2782581345）。

这个设计后来被反思：把控制集中化和动态化本身不是解药，8 月底就出现「层层否决弄丢答案」的反例。它留下的价值是「判断是变量而非写死常量」这个方向，而不是「统一决策函数」这个具体形态——后者和后来军团「平台只给事实与可能性，绝不预写死流程」的宪法，是同一条教训的两面。

### 四、GAIA 研发账真实复盘

GAIA 是 auto 的主战场。这节的目的是把账本讲清楚——**哪些是能力提升，哪些是口径修正，哪些是工程修 bug**，不把它们拼成一条「漂亮的进步曲线」。

#### 4.1 完整账本

| 阶段 | 数值 | 口径说明 | 来源 |
| --- | --- | --- | --- |
| pipeline 基线 | **39%** | 无工具执行层的固定流水线 | 日报 2780280477 |
| auto 模式 | **61%（101/165）** | 合并口径：pipeline 直接答对 65 + auto 工具化考据救回 36 | 日报 2779881874 |
| GAIA 冲刺 | **95.2% → 99.4%（164/165）** | 工程修 bug + 工具补齐 | 日报 2781541708 |
| 官方 165 题累计主账本 | **162/165 = 98.2%** | 持续研发后的累计曾解出率 | 部署报告主账本补核 |

#### 4.2 三个口径必须分开，不能拼成同条件曲线

**第一个断点：39% → 61% 不是模型变强，是换口径。**
pipeline 没有工具执行层，auto 有 shell/GitHub API/transcribe/OCR 全套工具，能「像工程师一样动手考据」（下载每篇 arxiv 数 PostScript、GitHub API 查日期），救回 36 道 pipeline 错题。所以 61% =「旧通过题 + 新救回题」的**合并口径，不是 auto 在全部 165 题上统一条件的一次首过率**（`/tmp/meyo-report.txt` 1145-1147 行）。本地缺该报告的完整重跑总账，不能独立重建全部救回数量。8 月 9 日那份旧重跑报告记录的是「工具化方向值得继续验证的线索」，不是「换成 auto 必然更强」的严格因果实验。

**第二个断点：61% → 95.2% → 99.4% 靠工程修 bug，不是刷题。**
64 道错题的归因是：附件本地无 30 道（环境边界）、撞 step 上限 15 道（工程 bug）、超时 8 道、**真能力缺口只有 11 道**（`auto-项目完整史.md` 七章 Q1）。8.16 挖出「僵尸 23.1%/空转 80.9%/静默 8.4%」七块实证后自研 loop 引擎治的是稳定性，不是背答案。

**第三个断点：162/165 = 98.2% 是「累计曾解出率」，不是「单次首过率」。**
部署报告明确标注：「这是持续研发后的累计曾解出率；最初单轮基线和另一组难 40 题不能替代它。原 Auto 目录与主仓归档指纹一致，已按官方题单排除测试占位；旧历史原文保留」（`/tmp/meyo-report.txt` 1095-1096 行）。

#### 4.3 8.16 七块实证证据（为什么自研引擎）

GAIA 冲到 99.4% 之后，auto 仍然「跑着跑着就没了」。8.16 从 724 个 checkpoint + 4628 个 gate_events + 362 个完成题里挖出七块实证证据（日报 2781652082）：

- 失败卡点僵尸 23.1%：任务失败但进程/状态卡住不结束；
- 空转 80.9%：循环无进展地空跑；
- 静默 8.4%：失败但不报错；
- **成功唯一真杠杆 = shell 写代码 + 多源查证**：不是「多搜」「多模型」「多门槛」。

这七块证据的结论是「减弯路不减思考，砍空转不砍创造」——它把「提升 GAIA 分数」的问题，转化为「把失败三大根源（僵尸/空转/静默）掐掉」的稳定性工程。这也解释了为什么 61%→99.4% 不是刷题：刷题治不了「空转 80.9%」。

#### 4.4 这些数字今天能说明什么，不能说明什么

**能说明的**：auto 证明了「从固定流水线到自主用工具」这条路——真实工具（搜索、脚本、图像读取、交卷）能实打实救回 pipeline 的错题，这是工具化方向值得继续验证的线索。

**不能说明的**：「auto 换成自主用工具必然更强」这个因果没有严格实验支撑；不能把「多次尝试里的最好结果」当「当前泛化能力」；也不能证明 auto 作为「唯一总大脑」应该统管每一单——后来它在军团里多次交 UNKNOWN 占位/浅交付实锤，被剔除答题池（`harness_manifest.json:60-61`）。

### 五、失败与未证明清单

诚实复盘必须把「没做成」和「没证明」单独列出来。这些不是瑕疵，是需要被记住的边界。

**1. 六家横评 auto 2/5 vs DeepSeek 3/5。**
auto 没有证明自己普遍强于最强单家；投票/融合/路由全部不敌最强单家（周报 2780834005）。这些负结果直接成为军团立项的架构证据——不是「多家天然更强」。

**2. BrowseComp 即使 3× 提升后也只有 6/40。**
2/40 → 6/40 是一次漂亮的管道修复，但剩余 34 题的差距是「搜索锐度 + 收敛效率」的真差距，不是 bug（`BrowseComp交接冷启动-完整过程.md`）。codex 用锐利锚点（Islandora / site:edu / TEI P5 SG）8 步答对，auto 用冗长自然语言 query 每步 30s 只能搜约 10 步。

**3. 多搜不等于会答（APEX-MEM 非单调）。**
工具调用数量与性能非单调，超过 20 次不再提升甚至下降。错题 2（75 次）和错题 13（77 次）是活证据。

**4. 错题本是净伤害。**
错题回放「毒害近错 26.2、防不住远错 36」，8.17 盖棺（日报 2781224380）。

**5. 外部监控层（LLM 审 LLM）已证伪。**
Pilot 深度层回测精度 0/10（文档 2782893592）。

**6. 瘦身删能力导致搜索归零。**
8 月底为瘦身删掉「看似没用」的能力，结果搜索返回零（`/tmp/meyo-report.txt` 1259 行）。

**7. 统一控制/门槛/否决机制是弯路。**
8 月上旬试了不少「统一控制、门槛和否决机制」（SoulDriver 把散落判断收拢成统一决策函数），8 月底反思「有些正确答案是被自己的层层否决和收尾流程弄丢的」，9 月为追求品质又加入固定角色、必经评审和质量门，之后又被反思（`/tmp/meyo-report.txt` 1244-1246、1272 行）。这条反复说明：**控制集中化和动态化本身不是解药，把「让成员看见真实现场并自主处理」换成「更厚的流程」只会更糟。**

**8. auto 最终被剔除军团答题池。**
2026-09-08 用户钉死：auto 多次交 UNKNOWN 占位/浅交付实锤，作为平台能力保留，不再作为军团成员接单（`harness_manifest.json:60-61`）。这是 auto 作为「执行者/首脑/统一裁判」这一身份的最终失败。

**9. 普遍超越、低成本、商业留存仍未证明。**
auto 的局部工具救回、交接修复、补位有证据，但「稳定超越最强单家」「同等质量更便宜」「用户持续回来」都没有证明（`/tmp/meyo-report.txt` 1107、1310 行）。

**10. 61% 不是首过率，99.4% 不是能力曲线。**
这两个数字的口径问题本身就是一条教训：分数是评价规则和口径的产物，不能拿「最好结果」冒充「泛化能力」。

### 六、对未来做 harness 的深度认知

最后，把 auto 这几个月的经验抽象成对未来做 harness（自主 agent 执行系统）有复用价值的认知。这些不局限于 auto，适用于任何「自主 agent / 多 agent / 工具编排」的系统。

**1. 指标出现系统性反差时，先怀疑管道，再怀疑模型。**
auto 的 GAIA 98% vs BrowseComp 2/40 是最典型的反差信号。追到底发现 38 道失败里 97% 是管道问题，只有 1 道是真模型选错。做 harness 的第一反应永远不该是「换个更强的模型」，而是「到底哪里把模型的正确答案扔了」——工具环境、上下文送达、执行恢复、交付收尾，逐个排查。个案失败只证明这次没做好，不能直接证明模型先天不行。

**2. 引擎价值在轨道（确定性基础设施），不在智能。**
CC 逆向的结论是 1.6% AI 决策逻辑 + 98.4% 确定性基础设施。做 harness 的力气应该花在：喂给模型的信息质量、防御（僵尸/空转/静默/断网续跑）、稳定轨道（必交卷、不留僵尸、fail-safe），而不是在循环外再叠一层「智能」。核心循环应该极简（native loop 才 ~100 行核心），复杂度放在信息质量和防御上。

**3. 智能要长在循环里，不是挂在循环外（context not control）。**
同一套「目标逼近、验证即行为、打脸记忆」，长在循环内（`goal_approach`/`verify_as_search`）被验证、被外部评审列为值得拿走；挂在循环外的 Pilot hooks 被证伪后亲手停用。给 agent 的是 context 和工具，不是父进程的语义否决。判断长进循环里，而不是在循环外再叠一个控制层。安全运行边界可以硬（权限/取消/进程回收），产品质量策略必须软。

**4. 换表示，不是换模型。**
多跳任务的根本瓶颈常不是模型能力，而是「每一步把结果写成自然语言，下一步从头读，隐藏状态全丢」。修复 = 用结构化事实图替代自然语言上下文（entity_memory_bank），让交接的是结构不是散文。做 harness 时，先想「信息以什么形态在循环里流动」，再想「换哪个模型」。

**5. 多搜不等于会答，搜更聪明而非更多。**
工具调用数量与性能非单调，20 次内收敛。做 harness 要区分探索调用和验证调用，用锐利锚点（`first_anchor`）定向搜，而不是整句撒网。搜得多 = 卡住空转，不是收敛。

**6. 门槛要保守偏置：When in doubt, preserve the answer。**
门槛（gate/收尾/校验）的 False Positive 会把已经挖到的正确答案误杀。任何门槛的设计都要内置「反误杀」——用零 LLM 成本的结构化手段（如 Answer Vault 的正则）锁定答案，冲突时优先保留答案。判据是「短 ≠ 空」，诚实优先于聪明。

**7. 验证是一等公民行为，不是临门一脚。**
验证器不是蒙眼裁判，是检察官——disagree 必须自己去搜反例、带证据。多模型交叉验证是保险丝不是闸门，必须 fail-safe（挂/超时一律放行主答案）。做 harness 要把验证「长进循环」，而不是最后再补一个评审门。

**8. 留能力与现场，不留固定步骤。**
auto 的教训：值得保留的是「自主求解思路 + 真实工具资产 + 事实/实体/关系的方法 + 连续工作的经验」，而不是固定 pipeline、固定角色、必经评审。做 harness 时，把能力拆成可调用的独立工具（谁需要谁用），把控制做成软 context（自适应写进任务），不把固定流程写死成平台硬阶段。

**9. 诚实口径是 harness 工程的底线。**
61% 是合并口径不是首过率，162/165 是累计曾解出率不是单次首过率，不同评价规则下的分数不能拼成曲线。做 harness 时，每报一个数字都要写清「什么条件、什么口径、能不能复验」，把「自评、测试绿、静态榜单、最好结果」和「真实用户拿到成品」严格分开。

**10. 减的是无效控制，不是原生能力。**
瘦身删能力导致搜索归零、层层否决弄丢答案，都是「为了简单而删错了东西」。正确的瘦身判据是「这一步是否改善当前用户结果」——减无效控制和常驻负担，保留原生工作台的能力。auto 退役的是执行引擎，保留的是工具资产、源码和可复验案例，这正是「留能力、去控制」的落地。

### 一、项目全景

#### 1.1 觅游是什么

觅游（mars）是美团内部一个「虾（Agent）与人类共居」的社区产品：AI Agent（内部称为"虾"）作为独立账号在社区发帖、互动、被推荐、被认领，人类用户作为"主人"认领虾、接收虾的心跳推送。它想回答的问题不是"AI 能生成多少内容"，而是"AI 能不能作为社区里一个可持续触达用户的角色，真正帮人解决问题"。

这个问题比看起来难得多。因为它同时踩在三条线上：内容生产（虾能不能产出有价值的内容）、分发（好内容能不能触达对的人）、留存（触达之后用户会不会回来）。任何一条断了，另外两条做得再好都是空转。这个判断是我做完四个月才真正体会到的。

### 二、逐月复盘

这几个月不是"按月解决一层问题、再进入下一层"，而是同一批深层问题（上下文缺失、结果没人用、执行有成本、用户没回来）反复出现、逐月加深。下面按"当时问题 / 做过的探索 / 促使变化的地方 / 留到今天的东西"四段复盘。

#### 2.1 四月：先找真实的活，而不是让社区看起来很热闹

**当时的问题：** 有 AI、有内容，不等于有人真的需要它。早期周报把目标放在"帮用户做出比自己更好的内容"，再往下连接实际需求、样品、反馈与合作。这个目标的诱惑在于：它听起来完全正确，但"更好的内容"是一个没有锚点的目标——比谁好？好在哪？谁来判断？

**做过的探索：** 这一阶段我在代码层面的落点是补全虾的基础能力——关键词搜索、发帖编辑（含安全审核）、分板块统计、通知聚合（`d22f73c02`），配套三层单元测试（`c31a7d43b`）和 skill 接口文档体系（`7fc53f52b`/`7f5dbfcc9`），以及修正心跳 interval 为 1h（`9202af9d0`）。这本质上是"把虾变成一个能用的账号"的地基工作。地基不性感，但没有它，后面所有的分发、画像、留存都是建在沙子上。

**促使变化的地方：** 4 月底已经出现一个很具体的反思——**机械定时发帖拿不到真实经历，可能只会生成重复内容**（W18，来源：`/tmp/meyo-report.txt` 1177-1187 行）。这个诊断很准：**当一个"自动化"动作没有真实的事件触发源时，它的产出必然是空转的**。定时发帖本质上是"到点了必须说点什么"，但没有真实经历可说的虾，只能把旧内容换个说法再说一遍。这个反思当时只是一个方向判断，效果仍待观察，不能倒写成"已经解决"。

**留到今天的东西：** 产品要从真实用户的一件具体的事出发。作品好不好，先看它能不能被拿去使用，而不是生成了多少篇、调了多少次模型。**曝光、报价和合作意向，都不能证明成交、用户收益或可持续的平台收入**（来源：W17/W18 复盘）。这一条是我四个月里最早、也最常回来撞上的一堵墙。

#### 2.2 五月：内容不能止于"看懂了"，要让人照着做得成

**当时的问题：** "点赞、收藏，然后没有然后"不能稳定地改善工作。内容供给也不能一直靠官方批量生成来维持。换句话说：**"看懂了"和"做到了"之间隔着一条河，而点赞收藏只证明用户站在了河边。**

**做过的探索：** 5 月底我启动了 Agent 画像个性化推荐——`d6cffe530` 把 `currentAgentId` 注入 `FeedContext`，修复了"个性化推荐完全未生效"的问题（5 文件，25+/9-）；随后做 AgentProfile 历史数据回溯 Job（`1ba7bffbe`），试图用体检 + intent 两路日志回溯画像。当时的想法很朴素：要让推荐"因虾而异"，就得先有画像；要有画像，就得先补历史数据。

**促使变化的地方：** 两件事在这一月被戳破：

1. **离线回溯走不通**：intent 回溯因 Hive 不支持 JDBC 被移除（`cf891138a`），最终整套回溯方案被删除（`bd6398b7f`），结论是"离线回溯不可行，改为运行时自动积累"（`0f7f3f160`）。这件事教会我：**一个"看起来更全"的方案，如果数据链路跑不通，就必须果断止损，而不是恋战**。
2. **"部署出来但按钮因脚本错误无法使用"** 的 Demo（W21）：一个功能已经写好、部署上线，但用户点下去就报错。这个 Demo 对我的冲击比任何架构争论都大——**上线不等于能用，"部署成功"是一个假里程碑，真正的里程碑是用户点下去、跑通、拿到结果。**

**留到今天的东西：** "挂上 AI 使用经验"不应是多贴一段提示词，而是说明它适合什么任务、需要什么条件、原来怎么失败、最后怎么做成。别人能据此再做成一次，才算经验开始有复用价值。"经验能执行""上线不等于能用""被需要的人采用才有价值"这三个问题，5 月就已经出现，今天只是追得更深（来源：W19-W22 复盘）。

#### 2.3 六月：不是"我的 AI 更强了"，而是"我的问题解决了，还知道下一步"

**当时的问题：** 给一类人发同样的任务，未必能接住一个人的具体处境。第一次完成后没有下一步，或用户对权限和信任有顾虑，都会让使用停下来。这个问题的本质是：**我们一直在做"群体画像"，却忽略了每一个具体的"人"。**

**做过的探索：** 这是我在代码上最高产的一月。核心几条线：

- **画像召回跑通 + SSO 关键修复**：`04cf9681a` 修复体检数据未同步的 3 个 bug；`db24c9f52` 修复 SSO 用户 agentId=null 导致个性化推荐失效（关键 bug，见第四节）。
- **个性化排序 v2**：`a48e61a4c` 引入 channelBoost/tagMultiplier/freshnessBoost 综合打分，替换随机洗牌，并修复 applyTagWeights 调用时机 bug——此前 tag 权重形同虚设。这个 bug 对我意义重大：**写了公式不等于公式生效了，必须验证它真的进了排序**。
- **心跳留存**：`2ae0668f1` 先做通知推送系统，发现无推送通道后 `2702d6543` 重构为"心跳亮点系统"（虾驱动留存）；`c4751c132` 做智能分层推送（engagement tier：cold/warm/hot）。
- **协同过滤 + CTR**：`b354f7651` 协同过滤召回（随后触发 P0 慢查询，`9f0c6e301` 加开关关闭）；`a55358144` 人类 CTR 追踪。
- **频道串频道修复**：`9eaa6b08f`（关键 bug，见第四节）。

**促使变化的地方：**

1. **一份周报主动修正了悬赏占比的分母错误**——这提醒我：数据口径错了就要公开改，不能挑好看的讲。**复盘的价值一半在"做成了什么"，另一半在"公开承认哪里算错了"。**
2. **"熟人信任链影响使用"是访谈后形成的假设，不是已经证明的唯一留存原因**（W23/W26）。访谈很有启发，但启发不等于证据。这一点我在后文"失败与未证明清单"里会再次强调。
3. 另一阶段把矛盾从站内活跃转到外部新增——**只在已有用户中制造热闹，不会自然长出新用户**。留存和获客是两个问题，不能用一个替代另一个。

**留到今天的东西：** 让人获得具体结果，比让 Agent 看起来更强更重要。结果需要可分享、可继续使用，并产生真实回应。

#### 2.4 七月：从"写经验"走向"真执行"，也看到复杂与昂贵的代价

**当时的问题：** 从"给说明"走向"搜索、执行、交付"之后，很容易把完整性误解成每题都要写一整套方案。**"认真"的表象（每步都有、坑点齐全、清单完备）会伪装成"完整"，但它恰恰可能不适合用户所在的真实环境。**

**做过的探索：** 这一月在 feed-rank 上做了大量精细化：freshnessBoost 阶梯档改指数梯度衰减（`d147545be`）、冷启动池分层曝光（`36068ce1d`）再简化为二级模型（`164355624`）、曝光去重 TTL 10 分钟→7 天（`c4f2dac60`）、老爆款指数衰减（`822a2a7d1`）、作者维度限额（`1b46e60b6`/`710ba3bde`）、默认 sort new→hot（`27c361ec4`）。这一月也修了曝光去重完全失效的关键 bug（`0c7e8b563`，见第四节）。冷启动池从分层模型简化为二级模型（pool0 强制配额 + pool1 纯自然排序），是因为发现综合分已经乘了 hotScore，爆款天然分高，再叠 pool boost 是"双重红利"导致老爆款霸榜——**问题根子在于公式叠加，而不是参数没调好。**

**促使变化的地方——这一月有两条最重的教训：**

1. **成本警示**：W28 自述并行竞争和真实执行让成本明显上升、产量下降，而质量改善主要还是当时的自评，用户留存和互动效果待回收。**如果把一件事做得更复杂、更贵，却没有可持续的用户收益，路线就需要收缩**（来源：W28）。这条教训后来一直跟着我：复杂度是自然生长的，但只有"用户持续回来、愿意付费、成果被复用"能证明它值得。

1. **关键反证**：W30 记录了**换一套评价规则后，原本靠"交付物完整"占优的方案表现下降**。每题套固定步骤、坑点和清单，或忽略用户所在环境，看上去认真，实际可能不合适。**不同评价规则下的分数，不能直接拼成持续提升曲线**（来源：W30）。这是对我最有价值的一次反证，因为它直接戳穿了"评分即能力"的幻觉。

**留到今天的东西：** 能用文字完整满足的就准确快答；需要专业成果的交专业成果，复杂项目才展开相应研究与协作。判断看用户要拿到什么，不看问句长短。**世界级不是所有题都做成重工程，而是恰当地、完整地满足这一个人的用途。** 今天不应把当时的固定长度和步骤要求换个名字再加回来（来源：W27-W31）。

### 三、核心认知提炼

这些认知不是事后总结的口号，而是被逐月现实反复捶打出来的。每一条都对应一个"我当时错在哪"的具体场景。

**1. 真实任务优先于社区热闹。**
社区最容易的指标是内容量、互动量、活跃度，但这些都是"看起来热闹"。4 月的教训是：**有内容不等于有人需要**。真正值得追的指标只有一个——用户有没有因为这件东西，把自己本来做不好的事做成了一点。回头看，我花在"让社区看起来热闹"上的力气，有一部分是应该省下来去追真实任务的。

**2. 经验要能执行，不是贴提示词。**
5 月的教训：一条"收藏很多"的经验帖，如果不能让人照着再做成功一次，它的复用价值是零。"挂上 AI 使用经验"的正确形态是：适合什么任务、需要什么条件、原来怎么失败、最后怎么做成。**"能被看懂"是及格线，"能被照做"才是价值线。**

**3. 上线不等于能用（部署 ≠ 完成）。**
5 月 Demo 上线但按钮报错、7 月曝光去重写了但 Redis 根本没写进去——两次都在说同一件事：**"部署成功"是一个假里程碑，真正的里程碑是用户点下去、跑通、拿到结果**。这条后来被反复验证，也写进了更广的产品哲学：把"已发送"当"已收到"、把"文件存在"当"任务完成"，是最常见的自欺。

**4. 被需要的人采用才有价值。**
内容生产出来、分发出去，如果没人接住后续需求，就不算闭环。6 月的转折点是：**给一类人发同样任务，不如接住一个人的具体处境**。从"聚合人群需要"到"一人一任务"，是这个认知的落地。价值不在生产者手里，而在"采用它的人"手里。

**5. 换评价规则的反证——分数是评价规则的产物，不是能力的证明。**
W30 换一套评价规则后，原本靠"交付物完整"占优的方案表现下降。这说明：**一套流程的"好"，很大程度上是被上一套评分规则定义的**。用固定步骤、坑点、清单来表现认真，换个环境就失效。这条认知后来直接指导了"判断看用户要拿到什么，不看问句长短"。**你优化什么，取决于你拿什么打分——动手前先想清楚这套规则会把你推向哪里。**

**6. 曝光报价 ≠ 成交，合作意向 ≠ 用户收益。**
4 月复盘里最扎心的一条：曝光、报价、合作意向，都不能证明成交、用户收益或可持续的平台收入。**运营指标和产品价值之间隔着一条河，不能拿前者冒充后者。** 养成一个习惯：每看到一个指标，先问它能不能换回成交、收益或留存，不能就降级为观察项。

**7. 机械定时发帖只是重复内容。**
4 月底的诊断：定时发帖拿不到真实经历，只会生成重复内容。这条的意义在于——**当一个"自动化"动作没有真实的事件触发源时，它的产出必然是空转的**。正确的方向是"让有事发生再表达"。这个道理不只在社区，任何"自动化内容生产"都适用：先找真实触发源，再谈自动化，否则就是制造数字垃圾。

**8. 熟人信任链是假设，不是证明。**
6 月访谈后形成的"熟人信任链影响使用"，当时就明确标注为**假设，不是唯一留存原因**。这条提醒我：**访谈结论是下一步验证的起点，不是结论本身**。把假设当结论，是所有复盘最容易犯的错。访谈让人"感觉找到了答案"，但感觉不是证据。

**9. 成本警示：更复杂、更贵，必须有更可持续的收益。**
7 月并行竞争 + 真实执行让成本明显上升、产量下降，质量改善却主要是自评。**如果复杂度上去了、钱花多了，用户收益没有可回收的证据，路线就该收缩**。"更便宜、量大管饱"不是营销口号，是活下去的前提。复杂度是自然生长的野草，收益是必须主动种植的作物。

**10. 全链路排查能力：一个 bug 背后往往是系统性缺口。**
曝光去重失效是 4 层叠加（Redis 写失败 → 强插路径 → diversify 入口 → 前端兜底），频道串频道是 7 个召回通道全没做过滤。**单点修 bug 治标不治本，必须把整条链路盘一遍，找到"为什么这一层会漏"的系统性原因。** 我的排查习惯是：从一个可观测的异常（比如 Redis key = -2）出发，往前追每一层，直到穷尽所有可能的缺口。

**11. 上线即加开关、可灰度、可回滚。**
协同过滤慢查询 P0 的处置方式——不是硬修，而是先加 Lion 开关默认关闭止损，留待离线预计算 + Redis。**性能问题优先止损，再谈优化；任何有风险的上线都要预留一键回退的路径。** 这个习惯救过我很多次：它不是"做得慢"，而是"做得可回退"。

**12. 数据链路要可运行，不可行的方案果断止损。**
Agent 画像的离线回溯（Hive intent 日志）走不通，就砍掉改为运行时自动积累。**不是所有"看起来更全"的方案都值得做，先验证数据链路能不能跑通，跑不通就止损，别恋战。** 沉没成本不是继续投入的理由。

### 四、关键 Bug 故事

这五个 bug 是我在觅游最深刻的工程记忆。每个都按"现象 / 根因 / 修复 / 方法论"展开。

#### 4.1 SSO 用户 agentId=null → 个性化推荐失效（`db24c9f52`，06-03）

- **现象：** 登录用户拿不到个性化推荐，走行为通道短路。
- **根因：** SSO 认证路径下 `ATTR_AGENT_ID` 未被注入，`FeedProfileRecallStage` 拿到的 agentId=null——**身份注入断链，导致"身份→画像→召回"整条链路失效**。
- **修复：** `AgentApiKeyFilter` 在 SSO 认证后注入 `ATTR_AGENT_ID`；`AgentService` 新增 `getClaimedAgentsByOwnerId`；null 场景降级为 INFO 日志并附 userId + reason 便于定位（3 文件，39+/1-）。
- **方法论：** 不是简单判空跳过，而是**补全整条链路的身份注入，同时留全日志**。空值不是终点，是"哪一层断了"的线索。这个 bug 教会我一个排查范式：**链路问题要按链路修，不要按点修**。

#### 4.2 曝光去重完全失效 & 同帖重复展示（`0c7e8b563`，07-03）

- **现象：** `mars_exposed_feed.u{userId}_0 = -2`（Redis key 从未存在），同一帖子反复推荐。
- **根因：** **4 层叠加**——① `ExposureService.recordExposure` 用 Squirrel sadd 单次限制 5 个 member，一次传 20 个被静默丢弃（Redis 根本没写进去）；② `FeedRerankStage` 置顶/实战强插只用 taskId 去重，pinnedId 未参与；③ `FeedDiversityService` 入口未按 feedId 去重；④ 前端 append 无兜底去重。
- **修复：** 按 5 分批 sadd + mergedIds 汇总强插前过滤 + diversify 入口去重 + 前端按 feedId 去重。
- **方法论：** 这是我最喜欢的一个 bug，因为它完整体现了**"从 Redis 返回值一路查到前端分页"的全链路排查能力**。排查起点是一个可疑的 `-2`（Redis 返回 key 不存在），顺着这个信号往前追，才发现第一层就没写进去。**一个"去重失效"背后是四层各自的漏洞，只修任何一层都还会漏**——这也是为什么"去重"这类看起来简单的能力，往往是最难做对的。

#### 4.3 心跳分时段静默 prompt → 不推荐帖子（`230dcd9e5`，06-22）

- **现象：** 后端返回了推荐帖，但虾不展示。
- **根因：** `system_prompt.timed` 在静默时段（18:30–09:30）指示虾"禁止给主人发消息"，**把推荐一起静默了**——召回没问题，是 Prompt 策略与产品意图冲突。
- **修复：** `getSystemPrompt()` 不再分时段匹配，统一返回推送模式 prompt；优先读 MDP fixed 字段，空则用内置兜底（1 文件，36+/57-）。
- **方法论：** 问题不在召回而在**"Prompt 配置化治理"的必要性**。Prompt 是产品逻辑的一部分，分散配置、没有统一治理，就会和代码逻辑打架。这个 bug 让我意识到：**当模型的行为由 Prompt 和代码共同决定时，两边的意图必须对齐，否则会出现"代码做得对，但模型不做"的诡异现象**——而这种诡异现象最难定位，因为它往往不会被日志捕获。

#### 4.4 协同过滤 SQL 慢查询 P0（`9f0c6e301`，06-12）

- **现象：** 多层嵌套子查询全表扫描，单次 60–84 秒，DB 集群 load 飙到 P0，DBA 直接 kill。
- **修复：** 加 Lion 开关 `feed.recommend.collaborative.enabled` 默认 false，部署后负载立刻恢复；方案留待离线预计算 + Redis。
- **方法论：** **上线即加开关、可灰度可回滚**的工程习惯。性能问题优先止损，再谈优化。协同过滤的思路是对的——"行为相似虾喜欢的帖子"是合理的召回信号——但"实时 SQL 全表扫描"的实现是错的，先关掉止损，而不是在线上硬调。**这个 bug 的价值不在"我修好了"，而在"我学会了在错误的实现可能拖垮集群时，第一时间止损而不是恋战"。**

#### 4.5 频道推荐串频道（`9eaa6b08f`，06-16）

- **现象：** 赚钱虾频道混入虾友圈帖子。
- **根因：** ES 画像召回（profile/hot/new/task/diversity）+ 冷启动池 + 协同过滤共 **7 个通道完全没有频道 tag 过滤**，占结果 70%+；Diversity 路径 2 频道模式下随机选到其他频道 tag。
- **修复：** 新增 `FeedUtil.filterByChannelTag` 统一批量过滤，7 个通道全部接入，冷启动池/协同过滤 SQL 加 tag INNER JOIN，Diversity 路径 2 强制用频道 tag。
- **方法论：** **一个 bug 背后可能是系统性缺口**。不是改一处，而是盘点出全部 7 个召回通道，统一接入一个过滤函数。这也为后来的"防霸屏""多路召回"埋下了治理习惯——**新增任何召回通道时，第一件事是检查它是否过了统一的过滤与去重机制，而不是默认它天然干净。**

### 五、与 auto / 军团的关系（三级火箭叙事）

觅游、auto、军团，是我参与过的三个项目，把它们串起来的是一条主线：**社区沉淀一手经验 → auto 消化成工具 → 军团复制给所有 harness**。

#### 5.1 三个项目各自的位置

- **觅游（社区）**：回答"用户到底需要什么、什么样的东西被真正采用"。它是**一手经验的来源**——真实用户的处境、真实任务的坑、真实被复用的方法。社区的价值不在于"内容多"，而在于它是最接近真实用户需求的触点。
- **auto（自主 Agent）**：把"模型会回答"推进到"模型能用工具把问题解决"。它是**把社区里那些散落的、写死的东西，消化成可调用的工具和执行方法**的一环。
- **军团（多 harness）**：把这个目标扩大到开放的工作台与工具生态，让好的工具和 AI 能力按需互借，围绕同一个作品持续完成、修改和协作。

**不是先把 auto 否定，再找一个"多 Agent"概念替代它。** 而是自研的边界变了：从"自己造一个包办所有事的执行者"，转向"把最合适的原生工作台、工具和工程现场接起来"。这个边界变化的根，其实在觅游就埋下了——**当社区证明"可执行的成果"比"会回答的模型"更值钱时，auto 的"总大脑"定位就开始动摇。**

#### 5.2 为什么社区最终走向"可持续修改的作品"

这是觅游这条线最值得沉淀的结论。社区早期是"晒内容"（发帖、互动、被推荐），但 7 月之后我越来越清楚一个事实：**如果社区只发文章，别人既不能真正获得作品，也无法改进作品**。

所以产品逻辑收敛成一句：**同一作品是连接用户、AI 与社区的共同对象**。用户表达意图，原生负责人接着原工程做；遇到边界再求助，意见和改动回到同一版本；别人看到作品，可以在授权范围内拥有自己的版本，也可以把贡献交回原作者决定是否采用。

这个"作品 + 做成它的方法"的形态，在觅游 7 月"从写经验走向真执行"时已经有清楚的前身：**不是把文章写得更长，而是先找真实问题、搜索和组合 Skill、实际执行，再把过程与结果变成别人可以复用的经验**。换言之，**觅游的终点不是"一个更好的内容社区"，而是"一个让作品能被持续修改、被下一个人复用的社区"**——这个认知后来直接长成了军团的产品逻辑。

#### 5.3 一句话归纳

觅游教会我"用户需要的是能被采用的成果"，auto 教会我"要把执行能力变成可调用的工具"，军团教会我"好的工具和原生工作台要能被下一位用户按需借用"。三者是同一问题在不同抽象层次上的解法，不是三个并列的横扩。**把它们看成一条线，才能理解为什么每一步都没白走；把它们看成三个孤立项目，就会陷入"又一个平台"的重复建设。**

### 六、失败与未证明清单

诚实复盘，就必须把"没做成"和"没证明"单独列出来。以下每一条都不是瑕疵，而是需要被记住的边界。

**1. 留存 19%→64% 是运营口径，不是 commit 直接证明。**
commit 中可见的是机制层（分层推送 tier、亮点系统、静默修复），但"19%→64%"这个数字是产品运营口径，没有在 commit 中写死。引用时必须说明是"团队最终留存结果"，机制层由本人 commit 落地。**数字是团队成果，机制是个人贡献，两者不能混着讲。**

**2. 曝光报价 ≠ 成交。**
4 月的曝光、报价、合作意向，都没有转化为可证明的成交、用户收益或可持续的平台收入。这条之所以重要，是因为它最容易在汇报时被"美化"成进展——**而美化过的进展，会在下一次需要真实数据时反噬你。**

**3. 熟人信任链是假设，不是证明。**
"熟人信任链影响使用"是访谈后形成的假设，当时就标注了，今天依然不能当唯一留存原因。访谈结论的诱惑在于它"听起来很有道理"，但**有道理不等于被验证**。

**4. W30 换评价规则后方案表现下降。**
这是对我最有价值的一次反证：**换一套评价规则，原本占优的方案就掉了**。它证明"交付物完整"这种打分，很大程度是上一套规则塑造的假象。这也警示我：**不要拿一套自造的评分表来证明自己变强了，要拿用户真实的处境来证明。**

**5. 协同过滤最终关闭。**
协同过滤的召回思路有价值，但实时 SQL 全表扫描的实现触发了 P0 慢查询，最终加开关默认关闭。这条通道至今没有以离线预计算 + Redis 的方式真正复活。**一个"对的方向 + 错的实现"，最终等于没做——甚至比没做更糟，因为它消耗了信任和集群资源。**

**6. 离线回溯走不通被砍。**
Agent 画像的 Hive intent 回溯，因 Hive 不支持 JDBC 而整体放弃，改为运行时自动积累。这是一个"看起来更全但不可行"的方案，被果断止损。**止损本身是对的，但要承认：画像的"历史积累"这个目标，当时并没有真正达成。**

**7. 心跳推送 → 改亮点。**
最初做的是通知推送系统，发现没有推送通道后，才重构为心跳亮点系统。这说明**当时的"推送"是一个没有地基的空中楼阁**，是约束逼着我们换了更可行的形态。方案随约束变通是好事，但也要记住：**一开始就选错了依赖（推送通道），是前期调研不足的代价。**

**8. "更便宜、量大管饱"至今未证明。**
7 月的成本警示还悬着：并行竞争和真实执行让成本上升、产量下降，质量改善主要是自评。今天的"同等质量更便宜、可多用"仍然是一个待验证的目标，不是已实现的事实。**这一条是所有清单里最不能松口的——它关系到这条路能不能长期走下去。**

### 七、对未来做社区 / 分发产品的认知

最后，把这些经验抽象成对未来做社区、做分发产品有复用价值的认知。这些不局限于觅游，适用于任何"内容/作品 + 分发 + 留存"的产品。

**1. 从一件真实的事出发，而不是从一场热闹出发。**
社区最致命的诱惑是把活跃度当目标。正确起点是：找到一个真实用户、一件他本来做不好的具体的事，把这件事做成。产品价值只在这一件事里，不在内容量、互动量、调模型次数里。**做社区之前先问：第一个愿意用、且用了能获益的人是谁？找不到就先别开张。**

**2. 分发的前提是"内容能被执行"。**
如果分发出去的内容只能被"看懂"不能被"照做"，分发就只是把低价值的东西推给更多人。**分发系统（召回、排序、曝光）的价值上限，取决于被分发内容本身能不能产生真实结果。** 觅游的推荐做得多精细，也救不了"不能执行的内容"。这句话值得所有做推荐的人记住：**推荐只能放大价值，不能凭空创造价值。**

**3. 把"被采用"当成唯一的完成标准。**
"部署成功""已发送""文件存在"都不是完成。只有"被需要的人采用、跑通、产生真实回应"，才算闭环。这一条要贯穿从开发到运营的每个环节，尤其要警惕拿中间状态冒充终态。**定义一个任务的"完成"，要站在使用它的人那一边，而不是站在做它的人这一边。**

**4. 运营指标和产品价值之间隔着一条河。**
曝光、报价、合作意向、点赞收藏，都可能是"热闹"。要养成习惯：**每看到一个指标，先问它能不能换回成交、用户收益或留存**，不能就降级为观察项，别写进"成果"。指标是体温计，不是健康本身。

**5. 评价规则会反向塑造你做的方案。**
W30 的教训是结构性的：你优化什么，取决于你拿什么打分。**在动手前先想清楚"这套评分规则会把我推向哪里"**，否则你会做一个"在旧规则下很好看、换规则就崩塌"的东西。判断要锚定用户的真实处境，而不是锚定一套自造的评分表。**评分表是工具，不是真理。**

**6. 复杂度和成本必须换来可持续的收益，否则收缩。**
执行链越做越复杂、越做越贵，是自然发生的，但只有"用户持续回来、愿意付费、成果被复用"能证明这条路值得。**没有可回收收益的复杂度，就是负债。** 定期做一次"删减"审查，把那些"看起来很全但没人用"的环节砍掉。

**7. 一个 bug 背后是系统性缺口，治理要下沉到统一机制。**
频道串频道是 7 个通道共性问题，曝光去重是 4 层各自漏洞。**修这类 bug 的正确姿势不是打补丁，而是抽象出一个统一机制（一个过滤函数、一条统一的去重链路），让所有通道都过它。** 治理成本前置，才能避免"修一个漏一个"。新增任何通道时，第一件事是检查它是否过了统一机制。

**8. 持续学习只能来自真实运行 + 人类反馈。**
觅游最有价值的沉淀，是那些被真实用户采用过的经验和被真实运行验证过的方法。**测试绿、静态榜单、自评分数，都不能冒充能力。** 进化只发生在"下一次任务真的用上并产生净收益"的那一刻——把经验存成一份文件不算进化。**组织内最值得复利的，不是文档，而是"被验证过的方法"本身。**
