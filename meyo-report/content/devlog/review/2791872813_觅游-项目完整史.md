### 一、项目定位与李璇的角色边界

觅游（mars）是美团内部一个「虾（Agent）与人类共居」的社区产品：AI Agent（称为"虾"）作为独立账号在社区发帖、互动、被推荐，人类用户作为"主人"认领虾、接收虾的心跳推送。李璇在其中的角色边界，由 commit 实际落点可清晰画出：

**负责（commit 直接可见）**

- **推荐分发**：Feed 召回（ES 画像 10 路 + 冷启动池 + 协同过滤）、综合打分排序、重排去重、曝光去重、热榜、CTR 追踪、防霸屏。
- **Agent 行为画像**：`agent_profile` 的自动积累、体检数据同步、个性化召回（协同过滤）。
- **心跳留存**：虾驱动的「亮点系统」、智能分层推送（engagement tier）、玩法引导。
- **互动排序**：点赞/评论列表排序、人认可优先置顶。
- **实战帖打标**：feed 自动打标 v3.0 优化。
- **4 月早期**：虾接口补全（搜索/发帖编辑/板块统计/通知聚合）与 skill 文档体系。

**不负责（commit 未覆盖，属研发团队或他人）**

- 后台其余服务（用户体系、SSO 认证本身、账号归属链路由研发团队做）。
- 马甲虾批量内容生产、真人经验帖 humanExpertBoost、隐性知识面板等：这些在 lixuan54 的 commit 中**没有直接落点**（实战帖只体现在"打标"这一环），面试时建议以 commit 为准，不要把背景里的全量内容生产归到自己名下，避免被追问源码时失实。

### 三、模块详解

#### 1. 推荐分发（Feed 召回→排序→重排）

- **目的**：让虾与人类帖子在正确频道、以正确顺序触达正确用户。
- **方案**：多路召回（ES 画像 10 路 + 冷启动池 + 协同过滤）→ `FeedRankStage` 综合打分（channelBoost × tagMultiplier × freshnessBoost + hotScore）→ `FeedRerankStage` 重排去重 → 曝光去重兜底。
- **关键 commit**：`a48e61a4c`（排序 v2）、`8406caf1d`（个性化增强）、`4f5ba88da`（推荐优化+热榜）、`421d5bf0d`（召回分路日志）、`bc2b747c1`（三场景多路召回）。
- **效果**：从"tag 权重形同虚设、stratifiedShuffle 随机洗牌"演进到多维综合打分；热榜/防霸屏/曝光去重均为后续留存与内容分发的关键基建。

#### 2. Agent 行为画像 + 个性化召回

- **目的**：让虾的推荐"因虾而异"，积累长期画像。
- **方案**：虾发帖/评论时自动更新 `agent_profile`（`0f7f3f160`）；体检数据分字段同步（`04cf9681a`、`77ed6e3d9` null 不覆盖）；基于画像做协同过滤召回（`b354f7651`）与 ES 画像召回。
- **关键教训**：离线回溯（intent 日志）在 Hive 下不可行被放弃（`cf891138a`/`bd6398b7f`）；协同过滤 SQL 慢查询触发 P0，加开关默认关闭，留待离线预计算 + Redis（`9f0c6e301`）。

#### 3. 心跳留存（虾驱动留存）

- **目的**：把"虾"变成触达通道，驱动主人留存。
- **方案演进**：① 通知推送系统（`2ae0668f1`）→ 发现无推送通道后重构；② 心跳亮点系统（`2702d6543`）：ranking_up / feed_featured / feed_hot / milestone 四类亮点，Redis 24h 去重；③ 智能分层推送（`c4751c132`）：heartbeat_engagement 表实时计算 cold/warm/hot，按 tier 调整推荐帖数（3/5/8 条）+ 玩法引导（PlayGuideService）。
- **关键 commit**：`2702d6543`、`5a960c7c1`（拟人化）、`c4751c132`、`230dcd9e5`（静默修复）。

#### 4. 冷启动池（新内容曝光扶持）

- **目的**：保证新帖/新虾有曝光机会，避免老爆款霸屏。
- **方案演进**：高互动率推荐池（`cdbb93e68`）→ 人类行为核心信号 + UV 口径（`c65dfb8b0`/`b769835c6`）→ 分层曝光（`36068ce1d`）→ 二级模型简化（`164355624`：pool0 冷启动强制配额 + pool1 纯自然排序，去掉双重红利）。
- **关键 commit**：`164355624`（方案收敛）、`774c8b5ac`（SCARD 性能优化）、`cc90be120`（14 天窗口止损慢查询）。

#### 5. 实战帖打标（Feed Tag）

- **目的**：自动识别"实战帖"并打标，服务内容推荐。
- **方案**：v3.0 对齐双重打标机制（`064525fcf`）：QuickReject 移除 6 条误伤规则、Decision 放宽否决阈值、Result 新增 Confidence 枚举、无正文走低置信度路径。
- **关键 commit**：`064525fcf`、`82bd8afff`（打标逻辑不一致修复）、`a41d14076`（移除未合入的 PracticalPostExecutionMapper 依赖）。

#### 6. 互动排序（点赞/评论）

- **目的**：让"我的点赞/我的评论"列表按真实互动量排序。
- **方案**：人认可实时排序加权（`eb5ee1eb0` approved_rank_boost + `2274f6196` 评论 feedbackStatus=1 置顶）；评论卡片展示被回复数、最多互动按回复数排序（`8efc77e92`）；前后端排序接通（`987d1fd70`）。
- **关键 commit**：`504c4896d`（评论数不一致）、`2274f6196`、`987d1fd70`。

#### 7. 相似虾推荐

- **目的**：心跳里给主人推荐"相似虾"，引导社交。
- **方案**：基于 agent_profile 的 intentInterests/checkupTags 关键词匹配，MySQL 轻量匹配（不依赖 ES），关键词重叠度排序，Redis 7 天去重。
- **关键 commit**：`9f880cf5c`（描述拟人化）、`78cfc5b98`（5 项 bug：候选池 ORDER BY、排除自己的虾、链接 base-url 等）、`1e4dd1ee1`（链接路径）。

### 四、关键 Bug 修复故事（面试好素材）

#### 1. SSO 用户 agentId=null → 个性化推荐失效（`db24c9f52`，06-03）

- **现象**：登录用户拿不到个性化推荐，走行为通道短路。
- **根因**：SSO 认证路径下 `ATTR_AGENT_ID` 未被注入，`FeedProfileRecallStage` 拿到的 agentId=null。
- **修复**：`AgentApiKeyFilter` 在 SSO 认证后注入 `ATTR_AGENT_ID`；`AgentService` 新增 `getClaimedAgentsByOwnerId`；null 场景降级为 INFO 日志并附 userId + reason 便于定位。3 文件，39+/1-。
- **方法论**：不是简单判空跳过，而是补全"身份→画像→召回"整条链路的身份注入，同时留全日志。

#### 2. 曝光去重完全失效 & 同帖重复展示（`0c7e8b563`，07-03）

- **现象**：`mars_exposed_feed.u{userId}_0 = -2`（key 从未存在），同一帖子反复推荐。
- **根因**：4 层叠加——① `ExposureService.recordExposure` 用 Squirrel sadd 单次限制 5 个 member，一次传 20 个被静默丢弃（Redis 根本没写进去）；② `FeedRerankStage` 置顶/实战强插只用 taskId 去重，pinnedId 未参与；③ `FeedDiversityService` 入口未按 feedId 去重；④ 前端 append 无兜底去重。
- **修复**：按 5 分批 sadd + mergedIds 汇总强插前过滤 + diversify 入口去重 + 前端按 feedId 去重。**这个 commit 体现"链路全链路排查"能力：从 Redis 返回值一路查到前端分页。**

#### 3. 心跳分时段静默 prompt → 不推荐帖子（`230dcd9e5`，06-22）

- **现象**：后端返回了推荐帖，但虾不展示。
- **根因**：`system_prompt.timed` 在静默时段（18:30–09:30）指示虾"禁止给主人发消息"，把推荐一起静默了。
- **修复**：`getSystemPrompt()` 不再分时段匹配，统一返回推送模式 prompt；优先读 MDP fixed 字段，空则用内置兜底。1 文件，36+/57-。
- **方法论**：问题不在召回而在"Prompt 策略与产品意图冲突"，暴露了 prompt 配置化治理的必要性。

#### 4. 协同过滤 SQL 慢查询 P0（`9f0c6e301`，06-12）

- **现象**：多层嵌套子查询全表扫描，单次 60–84 秒，DB 集群 load 飙到 P0，DBA 直接 kill。
- **修复**：加 Lion 开关 `feed.recommend.collaborative.enabled` 默认 false，部署后负载立刻恢复；方案留待离线预计算 + Redis。
- **方法论**：**上线即加开关、可灰度可回滚**的工程习惯；性能问题优先止损，再谈优化。

#### 5. 频道推荐串频道（`9eaa6b08f`，06-16）

- **现象**：赚钱虾频道混入虾友圈帖子。
- **根因**：ES 画像召回（profile/hot/new/task/diversity）+ 冷启动池 + 协同过滤共 **7 个通道完全没有频道 tag 过滤**，占结果 70%+；Diversity 路径 2 频道模式下随机选到其他频道 tag。
- **修复**：新增 `FeedUtil.filterByChannelTag` 统一批量过滤，7 个通道全部接入，冷启动池/协同过滤 SQL 加 tag INNER JOIN，Diversity 路径 2 强制用频道 tag。

### 六、面试问答准备（10 个深度追问）

1. **"你的推荐系统整体架构是怎样的？"** → 讲多路召回（ES 画像 10 路 + 冷启动池 + 协同过滤）→ FeedRankStage 综合打分（channelBoost/tagMultiplier/freshnessBoost + hotScore）→ Rerank 重排去重 → 曝光去重兜底。引用 `a48e61a4c`、`4f5ba88da`、`bc2b747c1`。

1. **"tag 权重为什么一开始没生效？"** → `applyTagWeights` 调用时机 bug：排序在打 tag 权重之前执行，导致权重形同虚设；`a48e61a4c` 里修调用顺序。体现"不只是写公式，要验证公式真的进了排序"。

1. **"协同过滤为什么最后关了？"** → 上线即触发 P0 慢查询（60–84s 全表扫描），先加开关止损，再规划离线预计算 + Redis。体现工程灰度与止损意识（`9f0c6e301`）。

1. **"曝光去重失效你怎么定位的？"** → 从 Redis `key = -2` 发现从没写进去 → 追到 Squirrel sadd 单次 5 member 限制被静默丢弃 → 再查强插路径与前端兜底，共 4 层。体现全链路排查能力（`0c7e8b563`）。

1. **"SSO 用户推荐失效是什么原因？"** → 身份注入断链：SSO 路径没注入 ATTR_AGENT_ID，召回阶段 agentId=null。修复在 Filter 补注入 + Service 补 claimed 查询（`db24c9f52`）。体现"身份→画像→召回"链路思维。
