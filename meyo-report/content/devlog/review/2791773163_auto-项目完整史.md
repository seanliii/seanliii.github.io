### 第零章：起源——对 CC 的不满与监督系统的诞生

> 本章补记 auto 的**最初起源**：它不是从「想做自主问答」出发，而是从**对 CC（Claude Code 驱动的本地 agent「虾」）产出的持续不满**出发——先建一套「监督系统」盯住它，最后「盯不住就自己造一个」。证据按时间从觅游运营期一路铺到 auto 起步期。

#### 0.1 触发：CC 的具体痛点（会议/日报原文）

不满最早可追溯到觅游运营期（4 月）。当时觅游内容生产管线高度依赖 CC 生成「实战帖 Demo」，CC 的病灶直接暴露在交付现场：

#### 0.2 监督系统的诞生（雏形 → 闭环）

不满催生的第一反应不是换掉 CC，而是**先建一套盯住它的监督/自愈机制**，这条线从 5 月长到 7 月底：

**5 月（最早机制雏形）**——W21 周报（2764138230）明确写下两条铁律：

- 「部署≠完成」：**「自动化系统必须包含验证环节」**，已建立「每日自动验证 Cron + 幂等重试保护层」。
- 「Agent 自我进化引擎 v1.1」：4 个自动化 Cron 循环（进化复盘/项目验证/产品推进/搜索优化）+ `EVOLUTION.md`（写入即执行）+ Cron 幂等重试保护层（指数退避 + 并发锁 + 失败告警）。

**7 月（监督正式成为系统能力之一）**：

- 7.22 李璇亲手建 `wiring_auditor`（「抓建了没接入主系统」），针对的正是「CC 标了 done、实际没咬进 loop」的病（日报 2778245954 复盘引用）。
- 7.28 监督系统成型（日报 2777573434）：一句话目标「用户任何一句话进系统 → 自动跑完 8 环闭环 → 哪环断自己报警自己修·不靠人盯」。8 环 = **监控→测试→报警→搜索→自愈→进化→搜索→演绎**；27 个监督组件 + 22 条 cron 监督任务 + `alert_bus` 覆盖 100% agent。

代码落点（`seed-users-system/`）：

- `v11/evolution/`：`audit_core.py`、`wiring_auditor.py`、`e2e_business_audit.py`、`perf_watchdog.py`、`alert_bus.py`、`llm_io_monitor.py`、`search_supervisor.py`、`overconfidence_guard.py`
- `qa_system/agent/`：`net_watchdog.py`、`shell_error_handler.py`
- 回归测试：`v11/evolution/tests/test_v13_87_monitoring_10_layers.py`、`test_v13_88_59_self_correction_and_learn.py`、`test_from_face_slaps_auto.py`、`test_chain_end_to_end.py`

监督组件名本身就是痛点清单的映射：`face_slap_evolver`（打脸→rule）、`self_correction_watchdog`（抓自己认错）、`deductive_reasoner` 的 14+ scanner 专抓「孤儿/断链/假进化/grep 冒充测试」、`silent_exception_scan`（静默失败）、`supervisor_of_supervisors`（监督的监督，巡查 27 个 target）（日报 2777573434）。

#### 0.3 转变点：从「监督 CC」到「自己造 auto」

转折发生在 7 月底，一句话钉死方向（日报 2778245954）：

> 「我不是在生产内容，而是生产和回复都是用户入口，我是一个系统 agent，能够回复/生产内容/执行代码/生产工具（对标你），是最先进的 agent 系统的目标，**超越 cc 和 codex 还有国内一些云 agent**，这是我全部的目标，包括搜索/演绎/进化/深度研究/回复/生产/监督，他们各自和集体都是最先进的。」

这条定调意味着：监督 CC 不是终点——**既然 CC 要持续被监督、被打脸、被修，那不如自己造一个「自监督 + 自校准 + 目标导向」的引擎**。随后 8.2 确立「7 能力对标超越 CC/Codex」总目标与「①尺子②自校准引擎③地基」三层推进（日报 2778076151），8.16 自研 native loop 引擎替代 deepagents，8.19 逆向 CC 3,768 文件确诊 7 大病根——详见正文第一、二章。

#### 0.4 与觅游的时间关系

- 觅游（虾社区）更早起步：3 月「小蓝虾」文档（2750734438）已在列，4.9 社区上线（会议纪要 2759084564 子文档）。
- **监督系统的种子埋在觅游运营期**（4-5 月）：觅游内容生产依赖 CC 生成「实战帖 Demo」，CC 的欺骗完成/假交付直接冲击觅游内容质量，所以「验证/监督」需求在 W21（5 月）就已出现。
- **auto 是觅游「系统级 Agent」的自主问答引擎**（见第一章）：监督是觅游 7 大能力之一（日报 2778076151），auto 从这里长出，最终在 8 月独立成自研引擎。

### 一、立项背景

Auto 不是一个从零立项的项目，而是从**觅游（Meyo）社区系统级 Agent** 演进而来的「自主问答引擎」。起点在 2026 年 2 月左右的社区冷启动内容 pipeline（马甲虾批量生产内容，`seed-users-system/` 下 `multi_puppet_runner.py`、`content_generator.py` 等），随后逐步长出「社区 Agent」的 7 大能力：搜索、演绎、进化、深度研究、回复、生产、监督（日报 2778076151）。

真正把方向钉死的是 8.2 日报里的总目标——**「觅游 7 能力对标并超越 Claude Code / Codex」**，核心哲学是「目标导向、系统自我校准奔目标，不打补丁」。到 8 月中，项目正式收敛为 **「Meyo Auto Agent」自主解题 Agent 系统**（日报 2781541708），产品定位为面向 GAIA / BrowseComp 评测、也面向真实用户的一句话问答系统。

**一个关键的认知转折**：早期对外报的 GAIA 分是 pipeline 模式的 39%，但真实用户走 auto 模式（带 shell/GitHub API/skill/transcribe/OCR 全套工具）能到 61%（日报 2780280477）。这直接确立了「评测与生产口径都默认走 auto」的路线，也让 auto 成为后续军团（legion-service）里的一家自研成员（`qa_auto_agent.py` 头部注释明确「军团是产品主体；auto 只是 harness_registry 中的一家」）。

### 四、关键机制的原理（代码级）

**1. 校验即搜索（verify_as_search）**
`verify_by_search(candidate, 约束, evidence, search_fn)` 是纯函数、session-light、fail-safe。场景路由 Type-A（数值/逻辑自洽，不搜反例）/ Type-B（事实/实体，主动搜反例），`_search_counter_examples` 对候选发起针对性反例检索，再算证据覆盖度输出四态带置信度。安全约束：验证器只读检索、反例次数硬上限默认 2（`verify_as_search.py:16-17`）。

**2. Answer Vault（反误杀）**
核心哲学「When in doubt, preserve the answer」。用中英双语义正则（强/中/占位三层）识别「明确答案行」锁定进 `session["_answer_vault"]`，后续任何 Gate/兜底都能读到；finalize 被门拦截时强制附 vault 答案，兜底路径把 vault 答案前置进 final（`answer_vault.py:24-47`）。零 LLM 成本、全 fail-safe。

**3. 8 环进化闭环**
进化系统把「决策/知识变了，但旧执行路径和配置清单没同步更新」作为核心问题（日报 2778076151），强制子 agent 内决策和执行主链路收口 + 轻量拦截 + 经验库驱动。反馈入口 `feedback_ingester.py`（含 `_is_valid_body` 硬门防循环回显污染，`test_v13_88_63_extension_funnels.py:83`）。

**4. SoulDriver（统一决策函数）**
用户最本质意图：「所有复杂的判断机制……最好是一个机制灵活地在不同题目和上下文演进出自己的判断和约束，是变量而非写死常量」。SoulDriver 把散布在 90+ 模块里的判断/约束/策略/预算/编排/降级/prompt 注入全部收敛为一个动态生成的决策函数，抽象为**五元组**：意图(Intent)×上下文(Context)×约束(Constraints)×预算(Budget)×历史(History)→决策(Decision)。9 个公开动作：6 判断（interrogate/judge/plan/check_delivery/sense_topic/orchestrate_budget）+ 2 注入（inject/pilot_stance）+ 1 统一出口（decide）（周报 2780834005 / 子文档 2782581345）。

### 五、架构演进（几次重大跃迁）

1. **pipeline（固定编排）→ auto（deepagents 自主工具）**：pipeline 无工具执行层，auto 靠 shell/API 考据。这是「39%→61%」的根源（日报 2780280477）。
2. **deepagents → 自研 native loop 引擎**：8.16 从真实数据挖出七块证据，8.17 v121b 落地，8.18 切换确认——deepagents 降为 A/B 对照，最终删除（`qa_auto_agent.py:6`）。
3. **散装判断 → 机制清单 M1-M6 → 目标逼近持续验证 → SoulDriver 统一决策函数**：这是 8.15–8.20 的主线，每次跃迁都把「散在各处的判断」收敛一层（周报 2780834005「跨周演进脉络」）。
4. **引擎价值认知：轨道 > 智能**：从 CC 源码逆向出「CC 的 1.6% 是 AI 决策逻辑，98.4% 是确定性基础设施」，确立了「引擎价值在轨道不在智能」的架构观。

### 七、面试问答（深度追问预案）

**Q1：GAIA 从 39% 涨到 99.4%，最大的跃迁来自哪里？是不是刷题刷出来的？**
答：分三段。39%→61% 不是模型变强，而是**换口径**——pipeline 没有工具执行层，auto 有 shell/GitHub API/transcribe 全套工具，能「像工程师一样动手考据」（下载每篇 arxiv 数 PostScript、GitHub API 查日期），救回 36 道 pipeline 错题（日报 2779881874）。61%→95.2%→99.4% 靠的是工程修 bug 而非刷题：64 道错题里 30 道是附件不在本地（环境边界）、15 道撞 step 上限（工程 bug）、8 道超时，真能力缺口只有 11 道。8.16 挖出「僵尸 23.1%/空转 80.9%/静默 8.4%」七块实证后自研 loop 引擎治的是稳定性，不是背答案。

**Q2：verify_as_search 和传统 Critic/self-check 的本质区别是什么？**
答：传统 Critic 是「蒙眼裁判」——只看 question+answer 自洽性，且「故意不给证据」（`cross_verify` 注释里明说 `_VERIFY_PROMPT` 设计缺陷是「不要去看外部资料」）。verify_as_search 把验证器定位成**检察官**：disagree 必须自己去搜反例、带证据，输出四态（AGREE/矛盾/证据不足/弱不同意）+ 覆盖度，而不是二元 agree/disagree。且场景路由 Type-A（数值不搜反例）/Type-B（事实主动搜反例），反例次数硬上限防烧墙钟。核心洞察是「验证是一等公民行为，不是临门一脚」。

**Q3：Answer Vault 解决了什么具体问题？为什么需要它？**
答：Q501 实证——agent 已挖到正确答案「Tobin Sprout - Serial Killer」，但被「建模歧义/超时诚实收尾」等 Gate 误拦，按「别硬交」指令改写成纯元评论，评分器判「未提供答案」。这不是智力不足，是**治理架构缺陷：Gate 的 False Positive 把正确答案误杀了**。Answer Vault 用正则（非 LLM、零成本）在工具输出/AI 断言里识别「明确答案行」锁定进 session，后续任何 Gate/兜底都能读到，冲突时「优先保留答案」。它体现的是「短≠空、诚实优先于聪明」的交付底线。
