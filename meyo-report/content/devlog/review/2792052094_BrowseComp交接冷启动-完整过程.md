### 三、技术细节（代码级）

#### 3.1 根因：交接冷启动

核心发现一句话（文档 2781609136 开头）：

> 你的 agent 平均 43 次工具调用、GAIA 98%，说明检索和推理能力本身没问题。BrowseComp 失败的根本原因是**多跳链条中的"交接冷启动"**——每一步推理把结果写成自然语言文本放入 prompt，下一步 agent 从头读取这段文本，之前步骤的 KV cache、attention pattern、隐藏状态全部丢弃。

#### 3.2 四种致命症状（20 道错题命中）

| 症状 | 论文 | 影响题数 | 典型案例 |
| --- | --- | --- | --- |
| 实体漂移 | ILCP-for-Agents + LLM Reasoning Failures | 4 道 | Arsenal→Celtic→Rennes（错题 5） |
| gold-in-thoughts 丢失 | Single-Agent vs Multi-Agent | 4 道 | Krasnodar 出现 2 次但最终选 Rennes |
| 宽松约束错锁 | Spurious Retrieval + APEX-MEM | 4 道 | Lil Pump 78% 通过所有宽松约束但漏了"越南裔" |
| 低置信硬交 | Fact-Level Calibration | 6 道 | conf 20% 自己说 not confirmed 还是交了 |

（文档 2781609136，命中了 6 篇顶会论文的 11 种失败模式。）

#### 3.3 修复前 vs 修复后（代码结构对比）

**修复前（自然语言传递）**——`entity_memory_bank.py:4-6` 把病根写死在模块注释里：

```
// 代码块
agent不是不会搜·是搜到的实体用自然语言传递·每次交接(工具结果→prompt→收敛)丢失隐藏状态。
足球题 Arsenal 在证据里 48 次·但最终推理里 0 次 = 收敛时把检索到的实体全丢了·凭 LLM 知识脑补。
```

旧方案是「事后从混杂 tool_log 正则提实体」，模块注释明确判定它「不可靠」——因为 tool_log 被心跳自省、元信息稀释，正则提不准。

**修复后（结构化事实图）**——三个模块把「交接」从散文改成结构：

1. `**entity_memory_bank.py**`（Layer 0/1）——在**工具结果落账的当下**就采集实体进结构化库：

```Python
// 代码块
# entity_memory_bank.py:81-101  observe_entities 的核心
session["_entity_bank"] = {entity_lower: {"name","hits","sources"}}
# 收敛时从结构化库选(而非从自然语言正则提)
# entity_memory_bank.py:120-184  rank_by_coverage
```

排序权重是「关联度（首要）> 覆盖率 > 频次」，专门治「部分覆盖但更有名/高频的错实体被选上」（`entity_memory_bank.py:159-163`）。

1. `**entity_drift_lowconf_guard.py**`（Layer 3/5）——纯逻辑检测原语，零 LLM 成本：

```Python
// 代码块
# P0-a 实体漂移：比对"答案断言的主体实体" vs "已多源确证实体"
# entity_drift_lowconf_guard.py:247-280  detect_entity_drift
# P0-b 低置信硬交：解析 "Confidence: 20%" / "not confirmed"
# entity_drift_lowconf_guard.py:81-105  is_low_confidence
```

文件头（`entity_drift_lowconf_guard.py:5-12`）记录了足球题的铁证：GOLD=FC Krasnodar，agent 交 Rennes；收尾时 agent 自述 "on loan from **Celtic**"，中间确证的母队 Arsenal 在收敛时被覆盖成 Celtic。模块设计原则三条：只检测不代答、fail-safe、有限次拦截。

1. `**first_anchor.py**`（Layer 0 上游）——治「C 模式撒网锁错实体 + 描述 query 搜不到 gold」：

```Python
// 代码块
# first_anchor.py:85-132  extract_anchors  正则锚点(引号短语 > 专名序列 > 数字短语)
# first_anchor.py:135-207  llm_extract_anchors  LLM 提"最独特约束组合"(语义判断)
# first_anchor.py:332-382  first_anchor_seed  提锚点→定向搜→提中间实体喂给下游 anchor_hop
```

诊断注释（`first_anchor.py:4-8`）说清了定位：13 道 bc 错题真 trace 显示主瓶颈是「首搜用整句描述撒网，锚不到可靠中间实体，所以顺藤链（anchor_hop）起不了步——anchor_hop 有下游、没上游」。本模块补的就是那一步上游。

### 四、完整反思过程（假设 → 验证 → 推翻 → 再假设）

1. **假设 A：不会搜**。验证：auto 平均 43 次工具调用，比 codex 搜得还多。**推翻**（文档 2781609136）。
2. **假设 B：不会推**。验证：GAIA 98%，推理能力没问题。**推翻**（文档 2781609136）。
3. **精读五遍失败题 + 十篇论文交叉验证**：把 20 道失败题逐条对照 6 篇顶会论文（Silent Failures、Fact-Level Calibration、LLM Reasoning Failures、Single-Agent vs Multi-Agent、APEX-MEM、ILCP-for-Agents），收敛到「交接冷启动」这一个架构级根因，并归纳出 11 种失败模式、4 种致命症状（文档 2781609136）。
4. **再假设：修复 = 换表示，不是换模型**。用结构化事实图替代自然语言上下文，落地 7 层架构（Layer 0 结构化事实图 → Layer 6 答案格式强制）。实施路线图按四周排（Week 1 治实体漂移 + Missing Memory，Week 2 治虚假检索 + 激活漂移，Week 3 治错锁 + 低置信硬交，Week 4 系统稳定性）（文档 2781609136「实施路线图」）。
5. **公平性审计的最终反转**：对 auto 的 38 道失败题逐条审计，发现**真正"模型选错答案"只有 1/38（3%）**，其余 37 道全是工程管道把答案扔了——其中 **finalize gate 拦死占 22 道（58%）**（文档 2782569511 四）。这把「模型能力问题」反转成「管道可靠性问题」。

### 五、最终结论与教训

结果（文档 2782569511）：**auto 2/40 → 6/40（3×）**，全程无作弊、无 gate 拦截、无 runaway。命中 6 题：Plastic Man、XML、Shivsagar Lake、07/28/1865、Bhowani Junction、1,000,000 quinine。其中 **XML 和 Bhowani Junction 都是原先被 finalize-gate 拦死的题**——修复后从「被系统扔答案」变成「搜索→收敛→答对」。

一句话总结（文档 2781609136）：

> 你的 agent 不是"不会搜"（43 次工具调用），也不是"不会推"（GAIA 98%），而是"搜到了但用自然语言传递，每次交接都丢失隐藏状态"。

最关键的方法论金句（对应文档 2782569511 的 97% 管道归因）：

> **当指标出现系统性反差时，先怀疑管道，再怀疑模型。** 38 道失败里 97% 是工程管道问题，只有 1 道是真模型选错。

### 六、面试回答脚本

#### 3 分钟版

> auto 在 GAIA 上到 95%+，但 BrowseComp 只有 2/40，这个反差本身说明有系统性 bug。我把 20 道失败题精读五遍，又拉了十篇多跳推理的顶会论文交叉验证，找到 11 种失败模式，最后收敛到一个根因：**每跳的结果被写成自然语言塞进下一跳的 prompt，KV cache、attention、hidden state 全丢**——就像让一个失忆的人接手前人的工作。

> 四种致命症状：实体漂移（题目问 Arsenal 球员，链条中滑到 Celtic→Rennes）、gold-in-thoughts 丢失（思考中已经出现正确答案，传递时丢了）、宽松约束错锁、低置信硬交（conf 20% 自己说 not confirmed 还是交了）。

> 修复不是换模型，是换表示：七层结构化事实图替代自然语言上下文，让每跳交接的是结构化事实而非散文。同时我做了公平性审计——先修了 6 个评测管道 bug（gold 泄漏、404 模型等），把对手 oracle 从 31/40 挤到 21/40，再修掉 auto 自己的 finalize gate 拦死问题。结果 2/40→6/40（3×）。

> 这个故事的价值不在提升数字，在方法：**指标出现系统性反差时，先怀疑管道再怀疑模型**——后来审计 38 道失败，97% 是管道问题，只有 1 道是真模型选错。

#### 追问应对

- **「交接冷启动有论文依据吗？」** → 有。核心是 ILCP-for-Agents（2026-07）和 APEX-MEM（ACL 2026）：多跳 agent 每交接一次控制权就丢弃上一 agent 的 hidden state，这正是我诊断的架构级缺陷。我同时命中了 Silent Failures、Fact-Level Calibration、LLM Reasoning Failures、Single-Agent vs Multi-Agent 共 6 篇论文的 11 种失败模式（文档 2781609136）。
- **「为什么不是多搜几轮？」** → 因为 APEX-MEM 已经证明工具调用数量与性能**非单调**——10 次约 75%，20 次后收敛到 80-85%，超过 20 次不再提升甚至下降。我的错题 2（75 次）和错题 13（77 次）完美验证了这点。关键不是搜更多，是搜更聪明：区分探索调用和验证调用，20 次内收敛（文档 2781609136）。
- **「具体怎么落地的？」** → 三个模块：`entity_memory_bank.py` 在工具结果落账当下采集实体进 `session["_entity_bank"]`（`{name, hits, sources}` 结构化），收敛时从库选而非正则提；`entity_drift_lowconf_guard.py` 做实体漂移检测和低置信检测（纯逻辑、零 LLM 成本）；`first_anchor.py` 提最独特锚点定向搜，替代整句撒网。
- **「数字 2/40→6/40 可信吗？」** → 这是 clean-room 重测：fresh session 隔离 + finalize gate 全移除 + 收敛信号 + 跨轮去重 + 无作弊，全 40 题跑出来的。而且我先审计了对手——他们名义 31/40 里有 10 题是先验/泄漏虚高，真证据只有 21/40。我连自己的分数也按最严口径报。
- **「如果面试官问剩下 34 题的差距在哪？」** → 诚实说：剩余差距是**搜索锐度 + 收敛效率**，不是 bug。codex 用锐利锚点（Islandora / site:edu / TEI P5 SG）8 步答对，auto 用冗长自然语言 query 每步 30s 只能搜约 10 步。这是搜索策略调优，不再是修 bug。
