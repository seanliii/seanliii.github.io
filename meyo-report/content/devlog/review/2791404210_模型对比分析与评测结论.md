### 一、模型清单与使用场景

军团（auto/legion）实际跑过的模型，按角色分层（来源：`model_rank_observer.py`、`model_registry.py`、`legion_core.py`）：

| 模型 | 角色 | 用途 | 代码依据 |
| --- | --- | --- | --- |
| `gpt-5.6-sol` | 主力钉 | 写代码/深度推理主力，能力档排序固定靠前 | `model_rank_observer.py` `PIN_PRIMARY` |
| `GLM-5.3` | 主力钉 | 中文/多模态主力，与 sol 并列为双主力 | 同上 + `model_registry._SCENE_MODELS` |
| `aws.claude-opus-4.7` | 兜底钉 | 锁末位、不参与重排，全链路兜底 | `ANCHOR_LAST` |
| `deepseek-v4-pro` | 性价比档 | 日常主力·性价比最优 | `_SCENE_MODELS["code"]["value"]` |
| `kimi-k3` / `MiniMax-M3` | 性价比/多模态档 | 中文、视觉（vision 场景 MiniMax-M3 已验证） | `_SCENE_MODELS` |
| `deepseek-v4-flash` / `GLM-5.3-flash` / `GLM-5.2` / `LongCat-2.0` / `gpt-4o-mini` / `deepseek-chat` / `Doubao-Seed-1.6-thinking` | 便宜快答档 | 省钱快答，战绩再好也不进能力档 | `CHEAP_TIER` |
| `vertex.*` / `aws.claude-opus-4.8` / `aws.claude-opus-4.6` | 死名单 | 上游封禁/历史坏账，绝不入池 | `EXCLUDE` |

**关键架构事实**：

- Vertex Claude 通道全灭，唯一活着的 Opus = `aws.claude-opus-4.7`（AWS 通道）。这是兜底钉锁死为 aws 版本的原因。
- 别名制统一（`select_usable_model` 里的 `_resolve_alias`）：耗尽/白名单过滤都先过别名解析，避免"耗尽过滤（别名≠真实值）永真、白名单∩池永空"绕过白名单的隐患。
- 场景映射（`model_registry._SCENE_MODELS`）：写代码/深度推理/长文共用一组，中文/快答/看图/生图各一组，每组再分 strong/value/cheap 三档。"快答"强调低时延靠**一次调用与跳过编排**，不把最终答案降级给便宜模型。

### 二、实测效果对比（真实数字）

#### 2.1 极简题耗时对比（各家 harness 稳定性差异，出处：日报 2783141021）

同一道"2+2"极简题各家耗时：

| harness | "2+2" 耗时 |
| --- | --- |
| penguin | 3.3s ⚡ |
| codex | 4.8s ⚡ |
| cc | 41s 🐢 |
| deepseek | >120s 超时 🐢🐢 |

> 结论：慢不是"架构慢/模型慢"，而是**特定 harness 本身极慢**（deepseek/cc 慢几十倍）。这是"聚合多家 harness"的真难点。

#### 2.2 GAIA 40 题三方对照（出处：日报 2783290420，同网关同题）

| 指标 | codex | deepseek | auto |
| --- | --- | --- | --- |
| 命中 | **33/40** | 19/40 | 22/40 |
| 空答案（no final） | **0** | 1 | **12**⚠️ |
| 崩溃（rc-9/parse_err） | **0** | 0 | 多个⚠️ |
| status=ok 率 | **40/40** | 40/40 | 7/40 |
| 均耗时 | **167s** | 310s | 510s |
| 均步数 | 37 | 109 | 37 |
| 均搜索 | 6.6 | 1.0（thinking off） | 13.4 |

> 最反直觉发现：**codex 赢不在"搜得多"（它搜 6.6，auto 搜 13.4），而在"100% 交付 + 0 崩溃 + 快 3 倍"**。auto 搜得最多却有 12 题交空白；未命中题搜 10 次/45 步 > 命中题 6.5/31 步——卡住时"thrash 空转"而非收敛。deepseek 本次是 thinking:off 的"关脑"配置，19/40 是"关思考+强制 seed search"下的表现。

#### 2.3 六家 5 题 BrowseComp 对照（出处：日报 2782515730，同 gpt-5.6-sol·temp=0·同 SearchFabric·1200s 墙钟）

| Harness | 命中 | 累计耗时 | 平均耗时 | timeout |
| --- | --- | --- | --- | --- |
| DeepSeek | **3/5** | 4645s | 929s | 2 |
| Codex | 2/5 | 467s | 94s | 0 |
| Auto（历史 best） | 2/5 | 5415s | 1083s | 0 |
| Hermes | 2/5 | 4789s | 958s | 0 |
| CC-agent | 2/5 | 1584s | 317s | 0 |
| deepagents | 1/5 | 605s | 121s | 0 |

> - DeepSeek 3/5 靠**事件溯源 + source anchor 坚持**（Eldorado 题唯一命中，始终保持 Blantyre Telegraph + Pro Wrestling Books 两个锚点逐层缩小）。
> - Codex 2/5 靠短环路+并行，但 **4/5 零搜索直猜**——低延迟 ≠ 检索最强，是"赌模型先验"。
> - Auto 2/5 = 功能最多、可观测最低、治理层最多。

#### 2.4 裸 CC 快的真相（出处：日报 2779137315，GAIA 9 题三方）

| Agent | 命中 |
| --- | --- |
| 裸 CC（opus） | 2/9 |
| qa_agent（pipeline） | 4/9 |
| auto_agent（deepagents） | 4/9 |
| **觅游（qa∪auto）** | **5/9（是裸 CC 的 2.5 倍）** |

### 三、关键结论（历史已得出的相对结论）

1. **codex 交付最稳**：33/40 命中 + 0 空卷 + 0 崩溃 + 167s。根因在架构——错误被 catch 成结构化事件、收尾在 finally 必然执行、中断抢救半成品，因此"没有跑很久交空白/进程猝死"的形态（日报 2783290420）。
2. **deepseek 搜索性价比最优**：把 harness_stats（各家命中率/中位耗时/搜索数）喂给模型后，**3/3 稳定自主选出 deepseek**（命中率 55%+中位 154s 性价比最优），此前无 stats 时选了慢的 cc（日报 2783141021）。但 deepseek 在极简题 >120s 超时——快题慢、难题强，是"持续工具迭代"型选手。
3. **搜得多 ≠ 对**（已证伪死路）：codex 搜 6.6 次拿 33/40，auto 搜 13.4 次只 22/40；auto 未命中题搜得更多（10 次）——搜得多=卡住空转，不是收敛（日报 2783142110）。
4. **多家答案 post-hoc 聚合/投票/路由全低于最强单家**（已证伪）：队长 v1-v6 全部 4/4/2/0/2/0 低于最强单家；deepseek+hermes 一致 11 题全错（一致≠正确）；topic 路由/LLM 5-fold 路由 15/40、12/40 都低于最强固定单家 cc 17/40（日报 2783142110）。
5. **加治理门/兜底/二模型否决 = 制造 empty_final**：把模型已写出的答案弄丢（final_authored_but_lost 11 题）（日报 2783142110）。
6. **GLM 推理护栏**：GLM 思考写 `reasoning_content`，小 max_tokens 会吃光预算（项目文档；CCR 插件已修）。这是"模型各留 2-3 个精选 + 思考型模型预算隔离"的工程理由。
7. **opus4.8 长会话间歇 404 → 降级 gpt-5.6-sol**（日报 2783141021，工程坑 6）：长会话不稳是旧主力 Opus 被 sol 取代的直接诱因之一。

### 四、评测与优化方法

#### 4.1 Wilson 95% 下界排序（`model_rank_observer.py`）

模型战绩来自军团真实运行账本 `~/.legion/model_health.json`（每家×模型 good/bad，`record_model_health` 每单落账）。打分用 **Wilson 95% 下界**（`p/(1+z²/n)` 下界公式），**小样本不虚高**——1 次成功不会把模型顶到第一。

规则（用户定稿"谁稳谁排前·自动替换"）：

1. 主力钉 `gpt-5.6-sol + GLM-5.3`、兜底钉 `aws.claude-opus-4.7`（锁末位不参与重排）；
2. 钉选主力也要资格赛：`n>=30 且 wilson<0.35` = 明确坏了 → 自动换下，战绩最优者补位；`n<10` 数据不足保持现位；
3. 能力档池自动发现（models.json programming 候选 + 实战新模型自动并入，新家零手改）；
4. `--apply` 才真写 models.json + 同步 CCR fallback 链，默认 dry-run。

#### 4.2 健康重排（`legion_core.select_usable_model`）

单次请求挑"当下真能用且本请求没试过"的模型 + appid：

- `trusted_appids` 白名单（已验证成功率高）优先；跳过 `known_broken_models` 坏模型 + `quota_exhausted_appids` 耗尽 appid；
- `exclude_models`：同请求失败后必须真换模型，不原地重试同一家；
- per-harness 健康重排：这家近期成功过的模型提前、连续失败的降后（`_health_bucket`，`good==0 且 bad>0` 沉底）；家×模型连败≥5 排序沉底但不硬过滤（给翻身机会）；静态结构性不兼容（如 cline×reasoning）hard 跳过；
- appid 轮换起点：全进程单调游标，并发 worker 天然分到不同 appid，避免全撞 trusted[0] 限流；冷却（429）appid 后置。

#### 4.3 战绩账本升降级（`record_model_health` / `_health_rank`）

- **只记可归因失败**：`gateway/rate_limit/provider/model_config/truncated/empty` 才记坏账；环境/Harness/工具/用户失败不记模型坏账（避免环境病污染排名）。
- **派单池纯净性**：capability/control-plane/ui-platform 家永不进答题池，写入口直接拦（browser-use 0/51 脏账实证）。
- `_health_rank = good - bad`：近期成功过靠前，连续失败多靠后，无记录中性 0。
- 跨进程写用 flock 文件锁 + 原子 replace（防并发丢计数），主进程按 mtime 失效重读（防 worker 子进程写盘后主进程用死数据）。

#### 4.4 新模型探测与复测纪律

- `biweekly_scan.py run`：候选名主动探测新模型（每两周扫描）。
- **复测必须串行**（不并行探测，避免大内存/网关并发干扰结论）。
- 四臂 A/B（`dev/benchmark_execution_modes.py`）：臂含 `strongest_single / fixed_three_parallel / legacy_legion / dynamic_legion`，另有 `direct_model`（主力模型直答）做裸模型对照；同题同预算、独立评委盲评，**只有声明"编排机制更优"时才跑同题四臂**，不日常烧四臂。

### 五、面试问答卡（7 个）

**Q1：你们怎么选模型的？**
答：分两层。**静态层**按"活的性质"映射场景（写代码/深度推理/长文共用 strong/value/cheap 三档），主力钉死 `gpt-5.6-sol + GLM-5.3`，兜底 `aws.claude-opus-4.7`。**动态层**用真实战绩重排——`record_model_health` 每单落 good/bad，`select_usable_model` 按家×模型健康重排候选、跳坏模型、绕耗尽 appid、appid 轮换错开。这是"context not control"：给客观战绩和可用性事实，不替 harness 写死某家绑某模型。

**Q2：模型坏了/变慢了怎么自愈？**
答：三层。①同请求失败后 `exclude_models` 保证**真换模型**（不原地重试同一家）；②健康账本把"明确失败且从未成功"的组合沉底；③跨方向兜底 `_select_cross_direction`——当前方向全失败时，回退到兼容面最广的 programming 方向的通用模型（仿 hermes `is_available()` 的"provider 不可用→回退 built-in"哲学）。都跑不了才如实失败，绝不假成功。

**Q3：你们怎么判断"哪个模型更好"，靠测试还是靠真实使用？**
答：靠**真实运行战绩**，不靠一次性测试。数据源是每单自动落账的 `model_health.json`，打分用 Wilson 95% 下界——小样本不虚高，1 次成功不会顶掉 100 次验证过的老模型。样本 `n>=30` 且下界 `<0.35` 才认定"明确坏了"自动换下；`n<10` 数据不足保持现位，防止拿偶然压人。

**Q4：你们做过哪些模型/编排层面的 A/B？结论是什么？**
答：做了四臂同题同预算盲评（最强单家/固定三并行/旧军团/动态军团 + 裸模型直答对照）。**目前没有证据证明"动态军团普遍优于最强单家"**，所以只有声明编排更优时才跑四臂，日常不烧；诚实保留单家/裸模型。同时一批方向被真实评测证伪：多家答案聚合、一致投票、topic 路由、靠"搜得更多"提分——全部低于最强固定单家，已进黑名单。

**Q5：真实场景里各家模型/框架的相对结论是什么？**
答：codex 交付最稳（GAIA 40 题 33/40、0 空卷、0 崩溃、167s），赢在"100% 交付 + 上下文 diff/压缩 + 退避降级"而非搜得多；deepseek 搜索性价比最优（harness_stats 喂模型后 3/3 选它，六家 5 题里 3/5 最高），靠事件溯源 + source anchor 坚持，但极简题超时——快题慢难题强；裸 CC 快是因为内置 WebSearch 轻量云端搜，不是纯模型底座强。

**Q6：为什么"搜得多"不是优势？**
答：GAIA 40 题里 codex 搜 6.6 次拿 33/40，auto 搜 13.4 次只 22/40，而且 auto 未命中题搜得更多（10 次/45 步 vs 命中 6.5 次/31 步）。搜得多 = 卡住时空转，不是收敛。所以优化方向是"信息增益驱动的早停 + 上下文压缩 + 收敛优先于穷尽"，而不是加搜索预算。

**Q7：新模型怎么引入？怎么保证结论可靠？**
答：新模型用 `biweekly_scan.py run` 候选名主动探测（复测串行）；能力档池自动发现（models.json 候选 + 实战新模型自动并入，新家零手改）。可靠性靠三条纪律：只记可归因失败（环境/Harness/工具/用户失败不记模型坏账）、派单池纯净性（capability 家永不进答题池）、同输入旧结果→重跑新结果→Δ 才算机制提分，测试绿只算"没崩"不算"更优"。
